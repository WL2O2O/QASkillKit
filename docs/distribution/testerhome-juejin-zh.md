# 我给 AI 写的测试用例找了个「改作业的老师」

## 先说结论

让 AI 写测试用例不难，难的是**证明它写得对**。

我把这件事拆成了两条通道：**规则断言**负责所有机械可判的事（列结构、优先级取值、追溯、跳转引用、空预期、虚构凭证、变更点覆盖），**LLM-as-Judge** 只评机器判不了的语义质量（场景充分性、相关性、一致性、幻觉）。门禁只认规则通道，裁判分数一律当参考。

这套东西现在是一个开源项目：[QASkillKit](https://github.com/WL2O2O/QASkillKit)，`git clone` 之后 30 秒、零 key 就能跑：

```bash
git clone https://github.com/WL2O2O/QASkillKit.git && cd QASkillKit
pip install pyyaml
python3 evals/evaluate.py
```

仓库自带 12 份用例：3 份好的通过，9 份故意写坏的（其中 8 份每份只坏一处，正好对应 8 条规则）全部被揪出。

这篇文章不讲怎么让 AI 写用例，只讲**怎么给 AI 的作业打分**——以及我在这个过程里踩的三个坑。

![双通道评测流程：用例+需求原文进入规则通道与 LLM-as-Judge，负向对照自测判别力，exit 0/1 放行或拦截](docs/assets/eval-gate.png)

## 坑一：让 AI 当裁判，它会「演」出核对过程

最直觉的方案是把用例和需求原文一起丢给大模型，让它打分。

我一开始就这么干。结果在 A/B 演示里翻车了：我把生成用例的 prompt 故意改弱（去掉追溯、变更点、表格规范等约束），产出的用例规则通道查出**变更点覆盖 0/5、缺变更点说明、6 列表格、4 处「同上」**——裁判却给了**四维全 5.0**。

更离谱的是收紧评分标准之后：裁判开始写「变更点 1、2、3、4、5、6 均覆盖」这种看起来很像核对过的话。但那份产出**一个变更点都没覆盖**，连变更点说明都没有。反过来，一份规则通道确认全覆盖的正样本，被它扣成「仅覆盖 3/5」——而那份需求的变更点一共只有 3 个。

结论很直接：**机械可判的事不能指望小模型裁判**。它会学会「核对的语气」，但结论是编的。

## 坑二：只靠规则，规则自己也会漏

那干脆全用规则？也不行。有两次真实漏检：

1. **表头漂移把行级检查一起藏了**。老实现遇到「列数 ≠ 9」的行，只报一条格式违规就 `continue`，后面 5 项行级检查全部跳过。那批产出正好是 6 列表格，里面的非法优先级、前置条件里的「同上」、缺失的追溯列**全部显示合规**。
2. **跳转引用的新写法**。「见上」「同上」这类词面写法好抓，但「执行 TC1 操作」——把前置条件寄托在另一条用例上——就漏了。而且这种写法比「同上」更隐蔽，读起来还挺自然。

修法都不复杂：表头不标准时**按列名兜底检查**；跳转引用里加「执行/参考/参照/复用/沿用 + 用例/TC + 编号」的分支（编号是硬门槛，所以「执行导出操作」不会误伤）。但这两次都说明：**评测器自己也要被评测**。现在这批规则有 190 条 pytest 锁边界，真实翻车产物直接当测试锚点。

## 所以：双通道 + 负向对照

最终的设计是这样的：

- **规则通道（零 key）**：8 条确定性断言，覆盖机械可判的全部内容。CI 和 pre-commit 只跑它——确定性的事不该依赖网络和模型。
- **裁判通道（有 key 才启用）**：4 个维度 1–5 分，及格线是均分 ≥ 4。它**只在规则通道放行之后**补充语义判断。
- **负向对照**：9 份故意写坏的样本，每份至少违反一条规则，用来证明评测器不是橡皮图章。判别力看「是否 detected」，不看裁判给几分。
- **三件套纪律**：改评分标准必须「升版本 + 重跑零 key 基线 + 重新校准」。这样任何一次「变好」都能排除「标准被调松」。

改 prompt 或换模型后想知道变好还是变坏，一条命令：

```bash
python3 evals/evaluate.py --diff 旧报告.json 新报告.json
```

逐用例逐规则列出退步/变好，退出码可以直接当回归门禁。裁判单维 ±1 的抖动不算退步——这是实测过的复跑噪声。

## 我给裁判本身也做了一套体检

既然裁判不可信，那就量化它有多不可信。三个指标，全部零 key 可离线重算：

1. **矛盾率**（`--judge-agreement`）：规则通道已经判定的事，裁判有没有给高于上限的分数。比如规则查出「优先级写了 P5」，上限要求 consistency ≤ 3，裁判给 4 分就是一次矛盾。离线重算历史报告：最早 67%，v4 收紧后 36%–54%，v5 把事实喂给裁判后掉到 4%–7%，v7 第一次做到 **0/14**。
2. **稳定性**（`--runs 3`）：同一份产出连评三轮，看极差和结论翻转。有一轮真实数据里，某条负向对照的 hallucination 打出 1→1→5，`pass@3` 只有 1/3——**同一份产出忽过忽不过，这种结论单跑一次不能采信**。
3. **反向可疑**：规则没有证据，裁判却压分。这条帮我们抓到了「把抽象占位『账号 A』当成虚构凭证」的系统性误判。

## 最新一版（v8）的诚实结论：部分达标

写下这些不是为了展示「我把它修好了」，而是因为**修不好的部分更有信息量**。

v8 一次攻三条裁判缺陷：抽象指代误判、编造 coverage 缺口、把「实际结果」列记录的产品缺陷当成用例的格式错误。除了改措辞，还把三样**机器核对过的事实**直接注入裁判 prompt（列结构无问题、变更点→用例名映射、产出里的抽象指代清单）——能算的事别让裁判算。

三次带 key 的重复评，逐次加料：

| 版本 | 反向可疑 | 矛盾率 | 结论 |
|:---|:---|:---|:---|
| 只改措辞 | 2 项 | 0/14 | 不达标 |
| + 机械事实 | **0** | 1/14 | 前两条达标，第三条仍 0/3 |
| + 禁用词 | **0** | **2/14** | 上限遵守反而退化 |

最刺眼的一次：裁判自己写出「但优先级列中出现了非法值'P5'」，然后 consistency 给了 4 分（上限 ≤3）。**事实承认了，上限没执行。**

所以 v8 的结论是：机械事实注入能治好「读不懂事实」，但 prompt 越长，小模型越容易顾此失彼。**措辞这条路已经到边际，下一版的上限应该由代码硬截断**（`score = min(score, cap)`），而不是继续加字。

三条没治好的 badcase 里，bc-0009 在验收达标后经复核标了 `fixed`；bc-0010 / bc-0011 保持 `confirmed`，修法还没落地——**半治好不算修好，也不会被写成修好**。

## 30 秒上手 / 想复刻的话

```bash
# 零 key：规则通道 + 全仓扫描
python3 evals/evaluate.py
python3 evals/evaluate.py --scan

# 评测器自测（零 key，秒级）
python3 -m pytest evals/tests -q

# 有 key：裁判 + 稳定性 + 一致性核对
export GLM_API_KEY=你的key
python3 evals/evaluate.py --runs 3
python3 evals/evaluate.py --judge-agreement evals/reports/xxx.json

# A/B prompt 回归（正式版 vs 故意弱化版）
bash evals/ab-demo.sh
```

想评自己的用例，一条命令登记：

```bash
python3 evals/evaluate.py --add 你的用例.md --fixture 需求原文.md --points ①②③
```

完整的评测方法、校准实录和 12 条 badcase 的根因分析都在 [evals/README.md](https://github.com/WL2O2O/QASkillKit/blob/main/evals/README.md)，所有数字都挂在 `evals/reports/` 的真实报告上，可以逐份复核。

如果这套「先证明评测器可信，再用评测器证明用例可信」的思路对你有用，欢迎在评论区聊聊你们团队是怎么验收 AI 产出的——我更好奇的是：**你们敢不敢把 AI 裁判的分数直接当门禁？**
