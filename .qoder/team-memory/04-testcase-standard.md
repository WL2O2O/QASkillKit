# 04 - 测试用例标准（命名 / 头部结构 / 归档）

## 用例命名规范（禁止编号前缀）

- **禁止**在用例名称中使用编号前缀（如 `①-1`、`②-3`）
- 使用**语义化简化文本前缀**，与「关联引用」列解耦
- 映射示例：
  - `①` → `默认值调整-`
  - `②` → `搜索框拆分-`
  - `③` → `最近登录-`
  - `④` → `Tab切换-`
  - `⑥` → `推送状态-`
  - 多变更组合（如 ①④）仍用首个主变更前缀

## 文件命名规范

- 格式：`{需求ID}-{需求标题}.md`（如 `1000001-【PC后台】入库管理-入库：支持修改入库单价.md`）
- 归档目录：`workspace/testcases/{迭代名}/`（hotfix 需求与迭代需求同目录，不单独创建 hotfix 目录；姓名子目录由用户自行创建）

## 文件头部结构（必须包含）

1. **标题**：`TAPD-{ID} {需求名} — 测试用例（mcpcase）`
2. **需求概述**：blockquote 格式概括核心变更
3. **设计依据与生成日期**
4. **变更点说明表**：变更编号（①、②、③...）、涉及位置、变更内容、说明
5. **主体测试用例**：按功能分组
6. **测试覆盖矩阵**：含关联引用列

## 用例内容原则

- **可独立阅读**：前置条件/操作步骤/预期结果禁止"见 xxx"跳转引用，每条用例自包含
- **数据来源标识**：测试数据需注明来源（如 TAPD 需求 / dbx 真实查询 / 知识库），引用真实数据（如真实入库单号）
- **关联引用**：通过变更点编号（①②③...）建立与需求描述的追溯链接
- **颜色标记**：以原型图中任意彩色标记（红/蓝/橙/紫/绿等）的正相关内容编写用例，不限于红色；全黑图片按新功能处理（全部注释文本为用例依据）；删除线文本表示功能移除不写用例；背景说明文字一般不写用例（含明确业务规则时兜底判断）
- **原型图注释核实**：注释面板文本需以 TAPD 需求标题/描述为权威，逐条判断是否属于需求范围；范围外的 UI 细节不得生成用例；不确定的标记为待确认项

## 用例分类组织

- 用例必须**按类型分类分组**，每个类别使用独立小节标题，提升可读性与直观性：
  - 正向流程 / 功能交互 / 边界值测试 / 异常输入 / 异常场景
  - 按钮防抖 / 兼容性测试 / 数据一致性 / 边界场景

## 预期结果表述规范

- 预期结果**必须包含具体的业务结果描述**，禁止"正常""正确""成功"等空泛表述
- 示例：❌"保存成功" → ✅"保存成功后列表页刷新，新增记录置顶显示且状态为草稿"

## UI展示预期与测试数据配套规范

- **用例表格列（6列带类型）**：`用例类型 | 用例名称 | 前置条件 | 操作步骤 | 预期结果 | 实际结果`；不设用例ID/模块/页面路径/关联引用/UI展示预期/测试数据建议列；UI 展示单独成条用例（用例类型=UI展示），其视觉细节写入「预期结果」列；「实际结果」列留空待执行时填写
- **按钮防抖必测**：凡涉及按钮点击的操作，必须配套「按钮防抖」类型用例（连点不重复提交/loading 期间按钮禁用等）
- **用例详细度**：每条用例必须详细覆盖「交互（操作步骤拆解到具体UI元素）+ 边界值（上下限/0/空/超限/特殊字符/重复提交）+ 需求关联性（跨模块联动校验）」三个维度，禁止一句话简略带过
- **UI展示预期**：UI 用例预期结果必须覆盖默认/悬停/点击/加载/错误/成功/空数据/权限受限态与响应式、文案规范；禁止笼统描述（"显示正常"→具体字号/颜色/对齐）；**UI 相关用例不得少于总用例数的 40%**；**原型/图片中每个 UI 元素至少一条用例覆盖**
- **原型链接全量分析**：需求中所有原型链接必须逐个打开分析，不得因数量多而跳过
- **变更影响分析**：每个需求输出直接影响点/间接影响链/回归范围建议/影响依赖矩阵，先影响分析再出用例
- **测试账号统一原则**：用例测试账号**尽量统一为 1 个主账号**（**品牌方总账号**，登录后进入供应商管理/员工管理等，用于新增测试数据）；涉及角色/权限/登录拦截的用例，测试对象为「员工管理」**新增的员工账号**（绑定业务员/采购员/拣货员/分拣员/仓管员/门店管理员等角色类型），**禁止把品牌方总账号绑定员工角色当测试对象**；仅特殊数据场景另用专用账号（如门店/仓库数据账号）；避免同一份用例中出现大量互不相干的账号，账号清单为私有信息，存于 `team-memory/local/test-accounts.md`（不入库），规则见 01 项目基础「PC后台测试账号」
- **账号≠数据，新增数据优先**：测试账号仅作登录身份，账号自带/绑定的数据不代表测试数据；用例所需业务数据以**新增为主**（前置条件写明创建方式，如“通过员工管理新增绑定客户 3 个”“新增 1 笔采购单”“用主账号登录员工管理新增员工账号 X”）；确需用存量数据时注明“以执行时实际为准”或先 dbx 确认存在；**禁止**把存量快照数字（绑定客户 64、经手 747）写死为断言依据，数量断言用相对式（新增 N 条 → 列表增加 N 条）
- **Skill自优化记录**：用例文档末尾输出本次新增规则/需修正旧规则/扩展建议，通用规则同步沉淀 SKILL.md 与 team-memory

## 数据一致性验证规范（订单/库存类）

- 涉及订单/库存/销量统计类需求，前置条件与操作步骤需支持数据库查询验证：
  - 订单状态为「已完成」、出库单商品明细与订单一致、库存扣减数量与出库数量一致
  - 库存流水记录对应扣库存操作、销量统计值与订单商品数量一致（无重复/漏计）

## Android/Win 双端模板化复用

- Android 与 Win 收银秤用例采用**模板化复用**：以 Android 版本为基准，全局替换关键词
  （`Android收银秤`→`Win收银秤`、`Android`→`Win`、需求 ID）快速生成 Win 版本，
  内容结构与覆盖点完全一致

## 输出与归档流程

1. 用例生成后归档草稿：`workspace/personal/drafts/{迭代名}/`（hotfix 需求与迭代需求放同一目录，不单独建 hotfix 目录；**目录不存在时自动创建**）
2. **正式归档**：复制到 `workspace/testcases/{迭代名}/`（**目录不存在时自动创建**；不创建姓名子目录，姓名分目录由用户自行移动归档）
3. 归档完成。注：`workspace/` 产物整体入库（生成后人工检查再提交）；仅 `personal/drafts/`（双路径归档的个人草稿副本）被 .gitignore 忽略

## 双路径核查修正规范（case-review）

- 用例文件双路径：正式路径 `workspace/testcases/{迭代}/` + 个人副本 `workspace/personal/drafts/{迭代}/`（hotfix 需求与迭代需求同目录查找，不单独查找 hotfix 目录；正式目录姓名子目录由用户自行创建，AI 定位用平铺路径）
- 有据直接修正后**必须同步两份文件**，并以 Node md5 校验哈希一致为准
- 文件末尾记录规范：直接修正追加「已修正 {YYYY-MM-DD}（有据直接修正）」逐条注明原型依据原文；待确认项保留，用户确认后追加「已确认」记录
- 增删用例后必须同步更新测试覆盖矩阵数量与合计

## 工具坑点：SearchReplace 长表格行替换

- **场景**：case-review 用 SearchReplace 替换含全角引号的长表格行（用例前置条件）
- **坑点**：返回「partial success（第一处失败）」时，**不代表另一处也未生效**——实测两处替换均已写入，导致文件末尾记录被重复插入两次
- **规避**：任何替换后（尤其含长行/特殊引号时）必须用 Read 重新读取文件验证实际内容；发现重复块立即清理；最终以 md5 双路径一致性为验收标准

## 工具坑点：需求标题含反斜杠导致目录化归档

- **场景**：TAPD 标题含 `\`（如 `1020257-【管理端\门店端-果运收银】…`）的需求，Windows 文件名不允许反斜杠，归档时被拆成「目录 `1020257-【管理端` + 子文件 `门店端-果运收银】….md`」结构
- **坑点**：双路径同步/定位脚本用 `fs.readdirSync().filter(f => f.endsWith('.md'))` 会跳过该目录；`path.join()` 会把 `\` 当路径分隔符误解析，导致文件被漏同步
- **规避**：定位与同步必须按目录递归处理（`fs.statSync().isDirectory()` 判断后进入子目录再枚举文件）；Read 直接读完整路径会失败（30404），先用 Node 脚本枚举真实目录结构

## 权限/角色类需求用例设计要点（1020253 沉淀）

- **角色拦截类需求**（如禁止某角色登录）：必须覆盖五类账号组合矩阵——仅拦截角色 / 拦截+含业务员组合 / 拦截+非业务员组合 / 正常角色 / 超级管理员，并验证：校验顺序（密码校验优先于角色校验）、多角色权限并集判定（任一角色命中即生效）、URL 直访绕过拦截（接口/路由层同样生效）、角色停用/软删除后的边界行为、账号禁用/锁定优先级
- **同角色多端校验规则可能不同**：同一角色组合在不同端（PC后台/猿后台/司机端）的登录校验规则可能不一致（如拣货员+业务员：PC后台拦截、猿后台放行），必须逐端核对 TAPD 描述分别生成用例，禁止「双端同规则」假设
- **多角色数据权限验证**：使用「对照组」方法——同一角色类型在单角色 vs 多角色状态下的数据范围差异对比（如仅采购员经手 N 条 vs 绑定多角色后全量 M 条，N<M），对照组通过员工管理**新增员工账号**配置；数量断言用**新增数据 + 相对式**（新增 N 条 → 列表增加 N 条），避免依赖存量快照数字，确需存量数据以 dbx 实时查询为准
- **真实角色绑定以 dbx 为准**：用例设计前必须核实角色类型/绑定关系的当前真实配置（禁止沿用历史假设或仅凭账号名推断角色），员工账号的角色绑定由用例执行时**新增配置**，绑定客户数/经手数等断言数字必须实时查询
- **多端登录限制需验证端间独立性**：同一账号在不同端（PC后台/猿后台/司机端）的登录限制相互独立，必须生成跨端对照用例（如仅拣货员禁止登录 PC后台/猿后台，但司机端可正常登录）
- **用例禁带表名与内部技术细节**：用例正文（前置条件/操作步骤/预期结果）不得出现数据库表名（如 tb_xxx）、租户ID、user_id、is_admin 等内部技术字段，测试数据来源标注为「dbx 真实查询」即可；数量断言使用**相对式/新增数据**（新增 N 条 → 列表增加 N 条），禁止写死存量快照数字

## 自检清单（关键项）

- 覆盖矩阵用例数量与表格实际条数一致（逐组求和校验）
- 无编号前缀用例名、无"见 xxx"跳转引用
- 低置信度 OCR 文本（score<0.7）不作为用例预期依据
- 测试数据与 dbx 真实查询结果一致（BIGINT 已 CAST 为字符串）
