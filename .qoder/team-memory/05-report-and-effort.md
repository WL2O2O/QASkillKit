# 05 - 周报统计 & 测试工时评估规范

适用 Skill：`weekly-report`（/zb）；测试工时评估规则供 `tseffort`（/tseffort）使用（tseffort 本地开发中，未随仓库发布）

## 周报统计规则

### 时间范围筛选（重要）

| 统计对象 | 时间字段 | 原因 |
|:---|:---|:---|
| 缺陷类 | `created` 时间范围 | 反映本周新发现缺陷；避免旧缺陷因后续编辑/状态变更被重复计入 |
| 需求类 | `modified` 时间范围 | 反映本周测试动作 |

### 缺陷筛选字段

- 周报缺陷统计用 **创建人 `reporter`** 字段（reporter=本人 + created 时间范围），
  反映本人本周亲自发现并提交的缺陷，避免因处理人流转（current_owner）导致漏计
- 注意：`get_bug` 返回字段中处理人为 `current_owner`，两者不要混淆

### 状态映射

- **必须动态获取**：调用 `get_workflows_status_map`（**必须指定 system 参数**）获取
  TAPD 实时状态映射，禁止硬编码/静态维护本地映射表
- 需求状态码 → 中文状态转换必须与接口返回严格一致

### 周报文件命名

- 周报文件命名**必须动态获取系统日期**，不得手工写死日期

## 测试工时评估规则

### 核心流程

1. 查询迭代 → 获取需求列表（**分页取全量**）
2. 剔除已有任务的需求（owner 含当前登录人昵称即跳过，不限【测试】前缀）
3. 按开发工作量（effort）评估工时
4. **强制先展示后确认**，禁止自动写入 TAPD
5. 用户确认后批量创建测试子任务

### 工时映射表（上限 2.5h）

| 开发工作量 effort | 测试工时 |
|:---|:---|
| ≤ 0.5h | 0.5h |
| ≤ 1h | 1h |
| ≤ 2h | 1.5h |
| ≤ 4h | 2h |
| ≤ 8h | 2.5h |
| > 8h | 2.5h（严格上限，不再递增） |

### 关键坑点

- **effort 含测试工时**：TAPD 需求 effort = 所有子任务（开发+测试）工时总和。
  二次评估时真实开发工作量 = 需求 effort − 已有【测试】任务工时，否则会虚高
- **分页防漏**：任务/需求列表查询必须按 `count.data.count` 判断总数，依次翻页
  （page=1,2,3...）直至累计 ≥ 总数；只取第一页会漏判"已有任务"需求（如 1018521、
  1017458、1017488 曾误判为待评估）
- **父需求跳过**：父需求（子需求在其他迭代）跳过评估、不创建任务，标注说明；
  无法判断时抛出人工介入
- **任务标题**：创建测试任务时标题**严格复用需求原始标题**，禁止简化/缩写
  （如【测试】前缀缩写）；批量创建后复查一致性
- **查询优化**：优先用 `owner` 参数直接过滤本人任务（一次请求完整结果、无需分页），
  避免拉全量再本地筛选

### 用户昵称获取

- 调用 TAPD 原生 API `https://api.tapd.cn/users/info` 获取当前用户昵称（`data.nick`），
  用于 owner 过滤
