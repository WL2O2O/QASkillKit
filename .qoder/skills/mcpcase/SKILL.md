# AI测试用例设计（MCP版）

## 使用方式

当用户输入 **纯数字**（如 `1019311`）或 **TAPD 前缀格式**（如 `TAPD-1019311`）时，
自动将其识别为**需求 ID**，按本 Skill 的完整流程生成测试用例。

### 示例
| 用户输入 | 自动识别为 |
| :--- | :--- |
| `/mcpcase 1019311` | 需求 ID 为 1019311 |
| `/mcpcase 1019311 @Spec文档路径` | 需求 ID 为 1019311，且通过 `@` 引用 Spec 文档 |
| `为 1019311 写测试用例` | 需求 ID 为 1019311（自动匹配）|

> **自动处理说明**：
> - **需求图片**：若 TAPD 需求描述中包含图片，AI 会自动下载图片并**调用 `/ocr` skill 完成三轨协同识图**，**无需手动调用 `/ocr`**
> - **原型链接**：TAPD 中附带的在线原型链接（如 modao.cc）**禁止**调用浏览器查看，以 `<img>` 贴图内容为准
>
> **可选补充信息**（按需提供）：
> - **Spec文档**：若有 Spec 文档，直接通过 `@` 引用文件即可，AI 会结合 Spec + TAPD 信息编写（以 Spec 为第一信息源）
> - **租户账号信息**：若需验证具体业务数据，可提供目标租户（tenantId）及登录账号密码
> - **额外要求**：如有特殊测试关注点，可在提示词末尾补充

## 第八步：数据来源规范（MCP工具调用规则）

### 8.1 测试数据获取规则（dbx MCP）

#### ⚠️ 前置必需：读取 dbx 工具 Schema

**在调用任何 dbx 工具前，必须先读取对应的 JSON Schema 文件**，否则 MCP 会报 "no tools registered"：

```
mcps/dbx/tools/dbx_list_connections.json   ← 每次会话首次必读
mcps/dbx/tools/dbx_execute_query.json      ← 每次会话首次必读
mcps/dbx/tools/dbx_describe_table.json     ← 需要查表结构时读
```

> **路径**：MCP 工具 Schema 位于 IDE 共享缓存目录，每台机器路径不同（勿写死具体盘符），定位方式：用 Glob 搜索 `**/mcps/{server}/tools/{tool}.json` 找到后 Read 即可

#### 连接信息与查询规则

- **连接信息从配置读取**：连接名取配置 `database.connection_name`（dbx 工具的 `connection_name` 参数），数据库名取 `database.database`（`database` 参数）；未配置时调用 `dbx_list_connections` 列出可用连接后向用户确认
- **唯一数据源**：所有测试数据**必须**通过 `dbx` MCP 从数据库获取
- **只读操作**：`dbx` MCP **仅允许执行 SELECT 查询**，**严禁** INSERT / UPDATE / DELETE / DROP / ALTER
- **禁止虚构数据**：用例中的会员名称、门店名称、订单编号、金额等字段，**严禁**凭想象编造
- **bigint精度**：查询含 `bigint` 类型的 ID 字段时，**必须**使用 `CAST(id AS CHAR)` 防止精度丢失
- **业务查询约定**：逐条遵守配置 `database.conventions` 中沉淀的项目约定（如临时数据排除条件等）
- **租户/账号确认**：编写测试用例前，**先判断需求是否涉及具体业务数据**。若涉及则主动询问用户目标租户（tenantId，可参照配置 `database.test_tenant_id`）及登录账号密码；若为系统配置类或总后台类功能则无需询问

#### 动态选表原则

**禁止固定套用**：根据需求业务领域动态判断需查询的表。通过 `information_schema.TABLES` 同时搜索 **TABLE_NAME**（英文表名模式）和 **TABLE_COMMENT**（中文注释），一次查询即可定位：

```sql
SELECT TABLE_NAME, TABLE_COMMENT FROM information_schema.TABLES
WHERE TABLE_SCHEMA = '{database.database}'
  AND (TABLE_NAME LIKE '%purchase%' OR TABLE_COMMENT LIKE '%采购%')
ORDER BY TABLE_NAME;
```

> **搜索技巧**：
> - `TABLE_NAME` 用英文关键词，英文表名关键词 → 中文业务含义的映射参照配置 `database.domain_keywords`（如 `order`=订单、`purchase`=采购）
> - `TABLE_COMMENT` 用中文关键词（`%订单%`、`%商品%`、`%采购%`、`%支付%`）
> - 两个条件用 OR 连接，总能命中

找到目标表后，用 `dbx_describe_table` 查看字段定义；需要样本数据时再用 `dbx_execute_query` 查询。

### 8.2 知识库补充规则（weknora-knowledge MCP）

- **触发时机**：当信息不足以支撑用例编写或业务细节不确定时，**先调用** weknora-knowledge MCP 调查
- **知识库选择**：从配置 `knowledge_bases` 读取知识库清单（`domain` 业务域 / `id` UUID），根据需求所属业务模块选择对应的知识库 ID 直接查询；配置为空数组时跳过知识库补充步骤
- **⚠️ 注意**：`list_knowledge_bases()` 和 `find_knowledge_base()` 目前会返回空结果，不要依赖它们搜索知识库，直接使用配置中的 ID 调用 `get_knowledge_base` / `list_knowledge` / `find_knowledge`
- **优先级**：Spec（若有）是第一信息源；知识库是补充信息源，两者冲突时以 Spec 为准

### 8.3 需求图片获取与 OCR 提取规则

- **触发时机**：TAPD 需求描述中包含 `<img>` 图片时，编写用例前**必须先**获取图片中的文字内容
- **获取图片**：调用 `get_image` 工具，传入 `workspace_id` 和 `image_path`，返回 `download_url`
- **📌 保存到缓存目录（重要）**：拿到 `download_url` 后，**必须**保存到 `workspace/personal/image-cache/{需求ID}/` 目录下（目录不存在则自动创建），禁止直接保存到项目根目录或其他位置（统一保存到缓存目录，供 case-review 按同名复用）：
  1. 先创建目录：`mkdir -p workspace/personal/image-cache/{需求ID}/`
  2. 下载图片到该目录：将 `download_url` 的内容写入 `workspace/personal/image-cache/{需求ID}/{文件名}`
- **链接时效**：`get_image` 返回的 `download_url` 有效期为 300 秒（5 分钟），需及时下载
- **图片缓存保留**（重要）：用例生成完成后**默认保留** `workspace/personal/image-cache/{需求ID}/` 下的图片，供后续核查复用（与 case-review 缓存策略一致：**case-review 核查时按 TAPD `<img>` 同名匹配优先复用该缓存目录，无需重新下载**；因此下载时**必须用 TAPD 原始文件名命名**，禁止自定义重命名，否则无法复用）。缓存截图随仓库入库，**提交前请人工检查是否含敏感内容**；若确需释放空间：`Remove-Item "workspace/personal/image-cache/{需求ID}/" -Recurse -Force -ErrorAction SilentlyContinue` 或要求 AI 清理
- **识图：调用 `/ocr` skill**（统一入口，不直接调用脚本）：图片就绪后，**调用 `/ocr` skill**（参数：图片路径），由 /ocr 完成三轨协同识图（Windows OCR 覆盖率 + OpenOCR 精读排序 + Read 结构理解）、交叉验证、置信度追踪与兜底处理，直接使用其返回的三通道融合结果：
  1. **融合文本**：Windows OCR 全量文字（含 `fixes` / `suspicious` 标记）+ OpenOCR 排序文本（含 `score` 置信度）
  2. **UI 结构描述**：Read 输出的按钮/弹窗/表单/下拉/颜色标记等结构信息
  3. **专项处理由 /ocr 负责**：浅灰小字、双色标注通读、大图 bbox 相对坐标、GLM 第二意见（含未配置自动降级）、人工切图兜底等细节见 `.qoder/skills/ocr/SKILL.md`，本 skill 不再重复实现
  4. **三通道交叉验证**：同区域文本互相印证，错别字在对比中暴露（如 Windows OCR 的"默 / 认" vs OpenOCR 的"默认"）
- **📊 OCR 置信度追踪（重要）**：从 `/ocr` skill 返回的文本块数据中解析每个块的 `score` 字段（0~1 置信度），**必须**执行：
  1. **提取并记录每张图片的所有文本块及对应 `score`**
  2. **标记置信度 < 0.7 的文本块**为「低可信度文本块」，这些区域的识别结果**不可靠**，不能直接作为用例编写依据
  3. 遇到低可信度文本块时，按以下优先级获取正确信息：
     - 🥇 **查 Windows OCR 同区域文本**：Windows OCR 对不同区域的识别精度可能不同，同区域文本可交叉验证
     - 🥇 **查 TAPD 需求描述原文**（`get_stories_or_tasks` 返回的 `description` 字段）
     - 🥇 **查 Spec 文档**（若有）
     - 🥉 **用 Read 工具复核图片**，但 Read 的描述必须与上述原文交叉校验
  4. **禁止**将低可信度 OCR 文本直接作为用例预期结果/文案的依据，必须找到原文确认
- **🎨 颜色标记识别（重要）**：需求图片中通常包含大量背景说明文字，仅标记了特定颜色（大多数为**红色**，也可能是蓝色、黄色等其他高亮色）的文字才是本次需求实际涉及的变更点：
  1. OCR 提取全部文字后，结合 Read 分析结果**判断哪些文字带有颜色标记**
  2. **仅以颜色标记的内容作为用例编写的主要依据**，未标记颜色的文字视为参考背景信息，**不得**为其编写测试用例
  3. 若同一图片中存在多种颜色标记，以红色（或产品/需求描述中明确提及的颜色）为主，其他颜色标记如需进一步确认，标记为待确认项
  4. 若 OCR 无法区分颜色（纯文字提取），需结合 Read 工具对图片的描述来推断哪些区域可能为高亮内容
  5. **黄色/彩色标注注释也要通读**：黄色/彩色标注注释可能与灰色说明文字冲突（如默认值、文案差异），两处都需读取并交叉核对，冲突时以 TAPD 描述为准并标记待确认项
- **⚠️ 原型图使用原则**：OCR 提取文字内容（规则说明、字段名称、提示文案、数值），Read 分析 UI 结构（按钮/弹窗/表单/表格等交互元素）；UI 颜色、弹性样式等视觉细节不作为预期依据
- **🔍 原型图注释/标注文本范围核实（重要）**：原型图片的右侧或上方常包含独立的**注释/标注面板**（如 "样式调整""取值调整""交互说明" 等区块），AI 需注意：
  1. 注释面板中的文本**可能同时包含**需求范围内的变更点（如 tab 切换）和范围外的 UI 设计细节（如按钮颜色、鼠标手型、文案措辞调整）
  2. **必须**以 TAPD 需求标题/描述（`get_stories_or_tasks` 返回的 `name` 和 `description`）为权威依据，逐条判断每条注释是否属于需求范围
  3. 需求范围中明确提及的 → 生成用例；**仅存在于注释面板中、需求范围未提及的 UI 细节 → 不得生成用例**
  4. 不确定的注释 → 标记为待确认项并提示用户
- **🚫 禁止调用浏览器查看原型链接**：TAPD 需求描述中附带的原型链接（如 modao.cc 等在线设计工具链接）**不得**通过浏览器打开查看。原型设计内容以需求描述中直接贴出（`<img>` 标签）的图片为准

> **说明**：识图流程由 AI 自动调用 `/ocr` skill 完成，用户无需手动调用 `/ocr` 命令。若 OCR 无法有效提取文字，/ocr 会提示人工切图。

### 执行顺序建议

1. **获取需求信息**：通过 TAPD 获取需求描述（有 Spec 文档则优先以 Spec 为准）
2. **调用 `/ocr` skill 识图**：若需求描述中包含 `<img>` 图片，调用 `get_image` 获取 `download_url`，**优先下载到 `workspace/personal/image-cache/{需求ID}/`**（目录不存在则自动创建），然后**调用 `/ocr` skill**（参数：图片路径）完成三轨协同识图：
   - **获取融合结果**：三通道融合文本 + UI 结构描述 + 每个文本块的 `score` 置信度
   - **低可信度文本标注**：标记 `score < 0.7` 的文本块，这些内容**不可直接使用**，需查 Windows OCR 同区域文本或 TAPD 需求原文确认
   - **颜色标记识别**：结合 /ocr 返回的 Read 结构描述，**判断哪些文字带有颜色标记（大多数为红色）**，仅以颜色标记的内容作为本次需求变更点；**黄色/彩色标注注释与灰色说明文字都要读**（两处常有冲突信息，冲突时以 TAPD 描述为准并标记待确认项）
   - **旧功能排除检查**：对原型图中的每个 UI 元素，确认它是否是本次需求的变更点（有颜色标记），**非变更点的旧 UI 元素不得生成测试用例**
   - **三通道交叉验证**：Windows OCR 文字 vs OpenOCR 文字 vs Read 结构描述，同区域文本互相印证，发现遗漏和错别字
   - 若 OCR 识别效果不佳，/ocr 会提示人工切图，按提示引导用户切图后重新提供
   - 注意：需求描述中附带的原型链接（如 modao.cc）禁止调用浏览器查看，以 `<img>` 图片内容为准
3. **标记信息缺失点**：结合需求描述 + OCR 文案 + Read 结构描述，识别信息不足处，调用 weknora-knowledge MCP 查询补充
4. **获取测试数据**：若涉及具体业务数据，确认租户后调用 dbx MCP 获取真实测试数据
5. **生成测试用例**：基于完整信息生成测试用例
6. **保留图片缓存**：图片默认保留在 `workspace/personal/image-cache/{需求ID}/`（供后续 case-review 核查复用，避免重复下载）；如需释放磁盘空间可手动删除该目录或要求 AI 清理

## 第九步：OCR 原文反查校验（Review）

生成测试用例后，**必须**执行 OCR 原文反查校验，确保用例与需求原文一致：

### 校验方法

1. **逐条比对**：拿着 OCR 提取的原文（或 Spec 原文），逐一核对每条用例：
   - 用例中的**变更点/业务规则**是否在 OCR 原文中有明确依据？
   - 用例中的**预期结果/提示文案**是否与原文一致，有无曲解？
   - 用例中的**数值/状态/条件**是否与原文完全匹配？
   - 是否有原文中明确提到的规则未被任何用例覆盖？

2. **遗漏检查**：将 OCR 原文的每个要点标记为 ✅（已覆盖）或 ❌（未覆盖），确保原文无遗漏

3. **关联引用可追溯**：每条用例的「关联引用」列应能对应到 OCR 原文的某个具体段落/编号

### 发现问题的处理方式

| 问题类型 | 处理方式 |
|:---|:---|
| 遗漏未覆盖的业务规则 | 补充对应用例 |
| 预期结果与原文不符 | 修正预期结果 |
| 文案/数值/状态名错误 | 修正错误信息 |
| 自主臆测的额外内容 | 删除臆测用例 |

### 兜底情况

若 OCR 原文质量不佳（识别结果不完整、文字错乱严重），无法作为可靠的校验依据时：
- 若有 Spec 文档，改用 Spec 原文进行反查校验
- 若既无可靠 OCR 也无 Spec，提示用户人工复核重点用例

### OCR 置信度报告生成（新增）

生成测试用例后，若存在 `score < 0.7` 的低可信度文本块，**必须**在本次对话末尾输出 OCR 置信度报告，供用户参考排查。

> **⚠️ 禁止**：禁止将置信度报告的任何内容写入测试用例文件（`{需求ID}-{需求标题}.md`）中，也禁止写入独立的报告文件。

**输出方式**：在对话末尾以 Markdown 格式直接输出，不写入任何文件。

**报告内容**：

```
## OCR 置信度报告

| 序号 | 图片文件 | OCR原文（低可信度） | 置信度 | 通道来源 | 可能影响的用例 | 说明 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | xxx.png | 默认仓库 | 0.32 | OpenOCR | ①「入库默认仓库校验」 | 内容不可靠，需用户确认 |
| 2 | xxx.png | 缓荐 | - | Windows OCR | ②「缓存清空操作」 | 与 OpenOCR 同区域文本"缓存"冲突，需确认 |
```

**生成方法**：
1. 回顾 `/ocr` skill 返回的结果，提取 `score < 0.7` 的所有文本块（OpenOCR），以及 Windows OCR 中与 OpenOCR 高可信文本冲突的文本行
2. 对每个低可信度文本块，分析其内容可能影响的用例：
   - 将 OCR 原文关键词与测试用例中的「预期结果」「操作步骤」「前置条件」进行语义匹配
   - 如果某用例的内容依赖了该低可信度区域的文本信息，标记为「可能影响」
3. 在报告末尾添加说明：
   > ⚠️ 以上 OCR 识别结果置信度低于 0.7，内容可能不准确。请用户逐条核对，确认无误或提供修正内容。

**报告交付用户后，等待用户反馈**：
- 用户确认无误 → 保留当前用例
- 用户提供纯文本修正 → 按用户提供的文本更新对应用例

## 第十步：自检与经验沉淀

### 两模式自检清单

用例生成完毕后，根据是否有 Spec 自动聚焦对应项，逐项审视：

#### Spec 模式（有 Spec 时必检）

| 自检项 | 说明 |
| :--- | :--- |
| □ AC-xx 覆盖 | 每条验收标准至少生成 1 条正向验证用例 |
| □ Rxx 规则覆盖 | 每条业务规则至少覆盖 1 条校验用例，复杂规则有组合用例 |
| □ 状态枚举覆盖 | 每个状态值都有正向流转 + 逆向/异常流转用例 |
| □ 触发条件覆盖 | 布尔表达式的 true/false 分支都覆盖了 |
| □ 异常处理一致性 | 异常处理表中每条场景的文案和用户提示与 Spec 完全一致 |
| □ 范围外确认 | 范围外清单（X01-Xxx）未越界生成用例 |

#### 普通模式（无 Spec 时必检）

| 自检项 | 说明 |
| :--- | :--- |
| □ OCR 文本全覆盖 | OCR 提取的每条文案（规则说明/字段名称/提示文案/数值等）都有用例覆盖 |
| □ 颜色标记聚焦 | 确认仅以图片中颜色标记（红色等高亮色）的内容编写了用例，未将背景说明文字误作为变更点 |
| □ 变更点无遗漏 | 所有变更点已编号（①②③...）且每条都有对应用例 |
| □ OCR 原文逐条过 | OCR 原文的每个要点标记 ✅/❌，❌ 的已补齐 |
| □ AI 臆测排查 | 无原文未提及、纯属 AI 臆想的用例，有则删除 |
| □ 文案数值一致 | 预期结果/提示文案/数值/状态名与 OCR 原文完全匹配 |

#### 通用自检项（两模式共用）

| 自检项 | 说明 |
| :--- | :--- |
| □ 可独立阅读 | 前置条件/操作步骤/预期结果无跳转引用（"见 xxx"、"同上"） |
| □ 数据真实性 | 门店名/会员名/订单号/金额来自 dbx 真实查询，非虚构 |
| □ 按钮防抖 | 所有涉及按钮操作的场景已补充防抖用例 |
| □ 覆盖矩阵校验 | 各维度用例数量之和 = 实际表格条数 |
| □ 无技术术语 | 用例描述无数据库字段名、接口参数名、SQL 等技术标识符 |
| □ 旧功能排除 | 原型图中的旧 UI 元素（非本次需求变更点）未生成测试用例 |
| □ 低置信度OCR处理 | OCR 识别置信度 < 0.7 的文本块已通过 Windows OCR 同区域文本或 TAPD 需求原文确认正确信息，未直接使用 |

### 经验沉淀

若发现具备通用性的问题类型（如某类规则易遗漏、某类文案易曲解等），**自主决定**是否沉淀到 `SKILL.md` 并用 `UpdateMemory` 记录经验，使后续调用自动规避。

## 核心禁止规则（务必遵守）

1. **禁止虚构数据**：所有测试数据必须通过 dbx MCP 真实查询获取
2. **禁止跳转引用**：前置条件/操作步骤/预期结果中不得写「见 xxx」「同上」等
3. **禁止交互臆测**：对 Spec 或需求描述中未明确说明的交互行为，严禁主观臆测
4. **禁止数据行为猜测**：字段取值范围、是否为空、空值显示样式等不得主观猜测
5. **禁止原型UI视觉细节作为预期依据**：OCR 提取文案、Read 识别 UI 结构元素（按钮/弹窗/表单等）均可用于用例编写；但 UI 颜色、样式、布局尺寸等视觉设计**不代表最终实现**，不得以此作为预期结果的判断依据
6. **按钮防抖必测**：涉及按钮操作的需求，必须补充防抖测试用例
7. **禁止调用浏览器查看原型链接**：TAPD 需求描述中的原型在线链接（如 modao.cc）不得通过浏览器打开查看，原型内容以 `<img>` 图片为准
8. **仅以颜色标记内容为变更依据**：需求图片中存在大量背景说明文字时，**仅以颜色标记（大多数为红色）的内容作为本次需求变更点编写用例**，未标记颜色的文字视为参考背景信息，不得为其生成测试用例
9. **禁止技术术语**：前置条件、操作步骤、预期结果中的描述**必须使用自然语言**，禁止出现数据库字段名（如 `production_date`）、接口参数名（如 `tenantId`）、SQL 语句等技术标识符
10. **⚠️ 禁止将原型图注释/标注文本直接等同于需求范围**：原型图片的右侧/上方的**注释/标注面板**中，常包含 "样式调整""取值调整""交互说明" 等辅助性文本，这些文本中可能同时包含**本次需求变更点**（如 tab 切换）和**非需求内容**（如按钮颜色、鼠标手型、文案措辞微调等 UI 细节）。AI 须严格以 **TAPD 需求标题/描述**（`get_stories_or_tasks` 返回的 `name` 和 `description`）作为需求范围的权威依据，对原型图注释文本中的每条内容逐一判断：
    - **在需求范围中明确提及** → 生成对应用例
    - **在需求范围中未提及**（仅存在于原型注释中，属于 UI 设计细节）→ **不得生成测试用例**
    - 若不确定某项注释是否属于需求范围，标记为待确认项并提示用户确认

> **总结**：测试用例编写**只涉及需求功能逻辑**，**不涉及交互UI设计**。需求中的 UI 交互以最终 UI/UX 设计稿为准，用例阶段不做 UI 细节验证。
