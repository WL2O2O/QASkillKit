# TAPD 需求 UI 自动化测试

## 使用方式

用户输入**纯数字需求 ID**（如 `1019739`）或 `测试 1019739` 等表述时，自动按本 Skill 流程执行：
定位用例 → 分组规划 → browser-use 执行 → 回填结果 → 汇总。

### 适用范围边界（先判断，再决定流程）
- **适用**：需求涉及网页端操作（PC后台 / 总后台 / H5商城），需要浏览器实测
- **不适用**：收银秤、小程序、原生 App 等**非浏览器需求**——不进入 browser-use 流程、
  不操作页面；仅复用「第四步」的分组逻辑，输出**科学排序与执行顺序指导**
  （先测哪条、再测哪条、为什么这样高效：依赖关系/同页面合并/前置数据/安全边界），供用户手动测试参考

## 执行流程总览

| 顺序 | 动作 | 说明 |
| :--- | :--- | :--- |
| 0 | 通读团队记忆库 | README 索引 + 01 项目基础/03 MCP 规范/04 用例标准 |
| 1 | 定位用例文件 | 按需求 ID Glob 搜索，多文件时确认 |
| 2 | 解析用例表 | 提取优先级/关联引用/类型/名称/前置/步骤/预期/实际列 |
| 3 | 分组规划 | 按变更点+页面合并，输出执行批次计划，标注安全边界用例 |
| 4 | 环境准备 | 登录、导航到目标页面 |
| 5 | 批次执行 | 每批尽量复用页面状态，收集证据 |
| 6 | 造数协作 | 优先前端造数；批量更新给 SQL（用户执行），AI 继续测其他用例 |
| 7 | 结果回填 | 用例文件"实际结果"列写回（✅/⚠️/❌/⏸️ + 证据） |
| 8 | 汇总输出 | 统计、差异说明、待执行 SQL 清单、待用户手动测试项 |
| 9 | 经验沉淀 | 本轮坑点与解法按端分类写入 `references/local/{端}.md`，Skill 持续进化 |

## 第一步：通读团队记忆库

执行任何操作前，先读 `.qoder/team-memory/README.md` 及本次任务相关主题文件
（01 项目基础/03 MCP 规范/04 用例标准），遵循团队沉淀的规范与坑点，不得绕过。

## 第二步：定位用例文件

1. Glob 搜索：`**/*{需求ID}*`（如 `**/*1019739*`），同时覆盖：
   - 正式归档：`workspace/testcases/{迭代}/`
   - 个人草稿：`workspace/personal/drafts/{迭代}/`
2. 多个匹配时：优先正式归档目录中"实际结果"列未回填（最近生成）的文件；
   无法确定时列出全部让用户确认。
3. 找不到用例文件 → 提示用户先用 `/mcpcase` 生成用例，停止执行。

## 第三步：解析用例表

用例为 Markdown 表格，列：`需求ID+名称 | 优先级 | 关联引用 | 用例类型 | 用例名称 | 前置条件 | 操作步骤 | 预期结果 | 实际结果`。

解析要点：
- 逐条提取为结构化记录，编号（①-1、①-2...按行号）
- 标注：优先级（P0/P1/P2）、关联引用（变更点①②③）、前置依赖（登录/造数/特定数据）
- 记录"实际结果"列当前状态（已回填的跳过）

## 第四步：用例分组与执行规划

按以下维度分组并输出**执行批次计划表**（告知用户，开始执行）：

| 分组依据 | 合并策略 |
| :--- | :--- |
| 同一变更点/同一页面 | 同批次，复用页面状态连续执行 |
| 同一流程链路（如"新增→校验→保存→列表"） | 合并为一条操作链，一次走完覆盖多条用例 |
| 同一前置数据 | 同批次先统一造数 |
| 相似交互（多个输入框校验） | 同批次按参数轮换 |
| 安全边界用例（推送/强更/凭证/删真实数据） | 单独标注 ⏸️，不执行，抛给用户 |
| 依赖 SQL 批量造数的用例 | 归入"待 SQL"组，最后执行 |

规划原则：**能一起测就一起测**，一次登录、一次导航、连续操作，避免重复往返；
但每条用例仍需独立断言其预期结果，不得合并后只验证最终态。

## 第五步：环境准备

1. 打开浏览器（browser-use `navigate_page` 或 `take_snapshot` 确认当前状态）
2. 未登录则登录，**各端地址与账号规则见 `references/local/` 对应端文档**（团队私有，gitignore 不入库）：
   - 端文档不存在时：提示运行 `/setup` 或按 `references/env-template.md` 创建；也可直接向用户询问测试地址与账号后继续（不中断流程），并将确认后的环境信息落盘到 `references/local/{端}.md`
   - 敏感账号（如频繁更换的业务账号）**每次询问用户，不记录**
3. 导航到用例涉及的目标页面（URL 直连比菜单点击更稳定）

## 第六步：批次执行与证据收集

### 执行规范
- 每批开始前 `take_snapshot` 获取最新 uid（DOM 更新后旧 uid 会失效）
- 操作优先用 MCP 原生工具（`click`/`fill`/`select`）；UI 校验类操作必须真实点击，
  禁止用 JS `.click()` 绕过校验逻辑
- 需要输入文件时：`upload_file` 失效则用 DataTransfer 注入（见 common.md）
- 验证接口链路用 `list_network_requests`（支持按 resourceTypes 过滤）
- 瞬时提示（toast/modal/错误横幅）用 MutationObserver 捕获文案（见 common.md）
- 上传类慢/失败场景用 XHR 拦截器模拟（见 common.md）

### 证据记录（每条用例）
- 结论标记：`✅ PASS` / `⚠️ 与预期不符（差异）` / `❌ FAIL（缺陷）` / `⏸️ 未执行（原因）`
- 证据内容：页面观察 + 接口链路 + 截图路径（截图存 `_tmp/` 或 `workspace/personal/`，不污染归档）
- 与预期不符时：**记录实际表现与差异点**，不擅自改预期，标注"建议与产品/开发确认"

## 第七步：造数策略（SQL 人机协作）

### 硬性规则
1. **AI 禁止写数据库**：即使 dbx 有写权限也不得执行任何 INSERT/UPDATE/DELETE，
   dbx 仅用于 SELECT 只读查询（验证数据、查真实测试数据）
2. **造数优先前端业务操作**：凡能通过页面操作完成的数据准备，一律走前端，
   保证业务流转完整（SQL 直写会缺失中间流程，导致用例无法覆盖）
3. **SQL 只作为建议输出**：仅当"批量更新"能大幅提效（如批量改状态、批量置数）时，
   给出 SQL 供用户手动执行

### 执行时序（关键）
1. 梳理用例所需数据场景，区分：前端可造 / 需 SQL 批量造
2. **先执行所有前端可造数 + 不依赖 SQL 的用例**（不阻塞、不等用户）
3. 将需要 SQL 的用例放入"待 SQL"组，继续测其他批次
4. 全部执行完毕后，统一输出**待执行 SQL 清单**：
   - 每条 SQL：用途、目标表/影响范围、建议 WHERE 条件（先用 SELECT 验证命中）、
     执行后如何验证（关联用例编号）
   - 文案示例：`以下 SQL 请手动执行，执行后回复"已执行"，我将继续测试：用例①-5、②-3`
5. 用户执行 SQL 后 → 继续"待 SQL"组用例 → 回填结果

## 第八步：结果回填

- 用 SearchReplace 逐条替换用例文件"实际结果"列（保留原格式，一次尽量多替换）
- 标记格式：`✅ PASS（证据）` / `⚠️ 与预期不符：差异说明（建议确认）` / `❌ FAIL：现象` / `⏸️ 未执行：原因`
- 回填后必须 Read 验证替换结果
- **不追加核查记录块**（团队规范：用例文件末尾不保留记录块）

## 第九步：汇总输出

执行完毕输出汇总（对话中展示，不写文件）：
1. 结果统计：✅ PASS n 条 / ⚠️ 差异 n 条 / ❌ FAIL n 条 / ⏸️ 未执行 n 条
2. 差异清单：每条差异的用例、实际表现、与预期的差异点、建议（提缺陷/与产品确认）
3. 待用户操作项：
   - 待执行 SQL 清单（如第七步）
   - 需人工手动测试的用例（安全边界、真实文件选择器、推送/下载流程等）
4. 数据安全说明：测试产生的数据（如测试版本、OSS 残留文件）及影响

## 第十步：经验沉淀（Skill 持续进化）

本 Skill 的参考文档**按端分类**，每次测试都在沉淀经验：遇到过的坑下次直接套用解法，不重复踩坑。

### 记录时机（立即记录，不等测试结束）
- 遇到问题并找到解决方案 → 立即按格式记录
- 发现端特有行为（页面结构、组件特性、校验逻辑、接口链路）→ 记录
- 记录前先查对应端文档，已存在的不重复记录，可补充验证过的需求编号

### 记录分类（按端分文件，各自维护）

| 文件 | 适用端 |
| :--- | :--- |
| `references/common.md` | 通用技巧（所有端适用：注入代码/捕获/拦截器；入库开源） |
| `references/local/{端}.md` | 各端环境信息 + 端特有坑点（团队私有，gitignore 不入库），如 `local/pc-admin.md`、`local/root-admin.md`、`local/h5-mall.md`，文件不存在时按 `references/env-template.md` 创建 |

### 记录格式（追加到对应端文件）

```
### [功能/场景]
- **现象**：遇到的问题或端特有行为
- **根因**：原因分析
- **解法**：验证有效的解决方案
- **验证**：已用于需求 xxx 验证有效
```

### 执行前必读
- 每批执行前先查对应端参考文档，已有记录的坑点直接套用
- 测试时新增端特性 → 先在本轮记录，测试结束后统一落盘到对应端文件

## 安全边界（硬性禁止，违反即停）

- 更新/发布类操作标题必须含"**不要更新测试**"标识，避免影响真实用户
- **推送相关操作不执行**（开启推送、执行推送）
- **强制更新不开启**
- 涉及安全操作（凭证越权验证、删除真实数据、真实支付/退款）不执行，抛给用户手动测
- 不写入数据库（见第七步）
- 不删除/篡改他人数据；测试数据尽量隔离（测试账号、测试租户）

## 常见坑点（browser-use，跨端高频）

| 坑点 | 应对 |
| :--- | :--- |
| snapshot 后 DOM 更新，旧 uid 报 "No node with given id" | 重新 `take_snapshot` 取最新 uid |
| `fill` 不生效 | 必须显式传 `value` 参数 |
| `upload_file` 对部分 input 失效 | DataTransfer 注入 + dispatchEvent(change)（common.md） |
| toast/错误横幅瞬时消失 | MutationObserver 预埋捕获文案（common.md） |
| 上传太快无法测"上传中"状态 | XHR 拦截器 delay 模式（common.md） |
| 菜单点击跳转不稳定 | 直接用 URL 导航（`#/xxx`） |
| 页面未加载完成就操作 | `wait_for` 或重试 snapshot |

> 端特有坑点（上传链路、组件行为、校验差异等）按端查阅 references/local/ 对应文件。
