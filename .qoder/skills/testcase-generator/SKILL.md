# AI测试用例设计（MCP版）

## 使用方式

当用户输入 **纯数字**（如 `1019311`）或 **TAPD 前缀格式**（如 `TAPD-1019311`）时，
自动将其识别为**需求 ID**，按本 Skill 的完整流程生成测试用例。

### 单需求输入
| 用户输入 | 自动识别为 |
| :--- | :--- |
| `/testcase-generator 1019311` | 需求 ID 为 1019311 |
| `/testcase-generator 1019311 @Spec文档路径` | 需求 ID 为 1019311，且通过 `@` 引用 Spec 文档 |
| `为 1019311 写测试用例` | 需求 ID 为 1019311（自动匹配）|

### 多需求串行输入
当用户输入**多个需求 ID** 时，按本 Skill 的**串行处理规则**（见下节）逐个生成测试用例。

| 用户输入 | 自动识别为 |
| :--- | :--- |
| `/testcase-generator 1014622 1016371 1017479` | 空格分隔，3 个需求 ID |
| `/testcase-generator 1014622,1016371,1017479` | 逗号分隔，3 个需求 ID |
| `/testcase-generator 1014622,1016371,1017479 @Spec文档路径` | 多个需求 ID + 通用 Spec 文档 |
| `为 1014622、1016371、1017479 写测试用例` | 中文顿号/逗号分隔，自动匹配 |

> **分隔规则**：支持空格、半角逗号 `,`、全角逗号 `，`、中文顿号 `、` 作为分隔符。
> 混合分隔也可识别（如 `1014622,1016371 1017479`）。

## 多需求串行处理规则

收到多个需求 ID 时，**逐个需求串行执行**完整流程（获取需求 → 下载图片 → OCR 识图 → 分析 → 生成用例 → 自检 → 归档），当前需求完成后才进入下一个需求。所有需求全部生成完毕后，**再逐个调用 testcase-reviewer skill 进行用例核查（采用「有据直接修正」模式：证据链完整、结论唯一的差异由 AI 自动双路径修正并同步矩阵，无需用户人工执行 review；仅依据不足/歧义项抛待确认等用户确认）**。

### 核心原则

1. **需求间严格串行**：每个需求独立走完从 TAPD 获取到用例归档的完整生命周期，不与其他需求并发
2. **逐个完整闭环**：每个需求的「获取 → 识图 → 分析 → 生成 → 自检 → 归档」在同一个处理周期内完成
3. **核查统一进行**：所有需求的用例全部生成并归档后，再逐个调用 testcase-reviewer skill 核查
4. **进度可中断恢复**：每完成一个需求就输出进度报告，对话中断后用户可提供未完成的 ID 继续
5. **阻塞先跳过**：单个需求遇阻塞立即标记 ⏭️ 并继续处理下一个需求，不中断批次；全部完成后统一抛出需人工介入清单

### 进度报告规范

每完成一个需求后，输出进度报告（仅输出到对话，不写入文件）：

```
--- 处理进度 ---
已完成：1/12 个需求
- 1020034-【Win收银秤】退款界面：样式优化：5 条用例 ✅
当前：1020035-【Android收银秤】退款界面：样式优化 → 🔄 处理中
等待：1020039、1020040、1020041、1020189、1020192、1020278、1020387、1020256、1020257、1020265
---------------
```

> **状态标记**：✅ 已完成 / 🔄 处理中 / ⏭️ 阻塞跳过（注明原因）/ 其余为等待
>
> **阻塞跳过示例**（遇阻塞立即跳过并继续下一个，详见下节）：
> ```
> --- 处理进度 ---
> 已完成：2/5 个需求
> - 1014622-xxx：8 条用例 ✅
> - 1016371-xxx：5 条用例 ✅
> 阻塞：1017479-xxx → ⏭️ 跳过（TAPD 需求获取失败，重试 2 次仍报错）
> 当前：1020035-xxx → 🔄 处理中
> 等待：1020039、1020040
> ---------------
> ```

### 阻塞处理与人工介入（多需求专属）

**核心原则：遇阻塞先跳过，继续处理其他需求，全部完成后统一抛出需人工介入清单。** 禁止因单个需求阻塞导致整个批次卡死或无限重试。

#### 1. 阻塞类型判定（满足任一即标记跳过）

| 阻塞类型 | 判定标准 | 处理方式 |
| :--- | :--- | :--- |
| TAPD 获取失败 | 需求不存在 / 无权限 / 接口重试 2 次仍失败 | ⏭️ 跳过 |
| 图片不可用 | 下载失败 / 链接过期且无缓存复用 / 图片损坏无法识别 | ⏭️ 跳过 |
| OCR 识图失败 | 三通道全部失败且无兜底手段（GLM 未配置、无法人工切图） | ⏭️ 跳过，提示人工切图 |
| 关键信息缺失 | 涉及业务数据但租户/账号信息缺失，且无 Spec 可替代 | ⏭️ 跳过，提示补充租户信息 |
| 范围判定歧义 | 原型注释与需求范围冲突无法定夺 | ⏭️ 跳过，标记待确认项 |
| 低置信度无法反查 | score<0.7 文本块经原文反查后仍无法确认 | ⏭️ 跳过，标记待确认项 |

> **禁止跳过**：可通过 dbx 查询、知识库补充、TAPD 原文反查解决的信息缺失**不得**跳过，须完成自纠后再生成用例。

#### 2. 跳过规则

1. 遇阻塞时将「需求 ID + 阻塞环节 + 阻塞原因 + 建议解决方式」记入**阻塞清单**
2. **立即继续处理下一个需求**，不中断批次、不无限重试
3. 阻塞需求**禁止**生成臆测用例或兜底用例（宁可跳过，不可臆造）
4. 阻塞需求**不进入** testcase-reviewer 核查，在最终汇总报告的「需人工介入清单」中统一抛出

#### 3. 操作上限（防死循环）

| 操作 | 上限 |
| :--- | :--- |
| 接口重试（TAPD / dbx） | 最多 5 次 |
| OCR 识图 | 最多 5 轮 |
| 同一步骤连续失败 | 5 次即强制停止并标记跳过 |

#### 4. 最后统一抛出

所有需求处理完毕（生成 + 核查）后，在**全量汇总报告中统一输出「需人工介入清单」**（格式见「全量汇总报告」章节），逐条列出需求 ID、阻塞环节、阻塞原因、建议处理方式。用户处理后，将需求 ID 重新提供给 AI 即可从阻塞环节继续生成。

> **自动处理说明**：
> - **需求图片**：若 TAPD 需求描述中包含图片，AI 会自动下载图片并**调用 `/ocr` skill 完成三轨协同识图**，**无需手动调用 `/ocr`**
> - **原型链接**：TAPD 中附带的在线原型链接（如 modao.cc）**禁止**调用浏览器查看，以 `<img>` 贴图内容为准
>
> **可选补充信息**（按需提供）：
> - **Spec文档**：若有 Spec 文档，直接通过 `@` 引用文件即可，AI 会结合 Spec + TAPD 信息编写（以 Spec 为第一信息源）
> - **租户账号信息**：若需验证具体业务数据，可提供目标租户（tenantId）及登录账号密码
> - **额外要求**：如有特殊测试关注点，可在提示词末尾补充

## 第四步：明确不做的事情（范围外确认）

**核心目标**：确认需求中的排除范围，避免无效测试用例。

- 范围外清单（Spec 三、3.2 范围外 X01-Xxx）→ **不生成**对应测试用例
- 以产品/开发明确答复"本次不做"为依据

| 规则复杂度 | 从 Spec「4.4 业务规则」识别复杂逻辑 | 复杂规则增加组合测试用例 |

| 验收覆盖 | 从 Spec「八、验收标准 AC-xx」逐条映射 | 每条 AC 至少生成 1 条正向验证用例 |

## 第七步：生成测试用例表格

### 字段说明

| 字段名 | 说明 | 填写规则 |
| :--- | :--- | :--- |

| **关联引用** | 对应 Spec 中的 AC-xx / Rxx / 状态枚举 / 章节，或无 Spec 时引用变更点编号（①、②、③...） | 建立可追溯性，便于需求变更后快速定位 |

| **用例名称** | 简要描述测试点 | 建议格式：「[AC-xx] 场景描述」/「[Rxx] 规则验证」（有 Spec）/「简化前缀-场景描述」（无 Spec）<br>⚠️ 用例名称中**禁止**使用变更点编号前缀（如"①-1"），编号引用统一放在关联引用列 |
| **前置条件** | 当前操作前需要准备的数据或环境 | **必须**从需求来源中提取并转化为具体的、可操作的环境/数据描述，**禁止**写"见 xxx"类跳转引用 |
| **操作步骤** | 当前要操作这条用例的具体步骤 | **必须**将需求验收标准拆解为具体的操作动作，**禁止**写"见 xxx"类跳转引用 |
| **预期结果** | 需求的预期结果 | **必须**写明可观测的具体结果，**禁止**写"见 xxx"类跳转引用 |

### 测试用例表格模板

## 第八步：数据来源规范（MCP工具调用规则）

### 8.1 测试数据获取规则（dbx MCP）

#### ⚠️ 前置必需：读取 dbx 工具 Schema

**在调用任何 dbx 工具前，必须先读取对应的 JSON Schema 文件**，否则 MCP 会报 "no tools registered"：

```
mcps/dbx/tools/dbx_list_connections.json   ← 每次会话首次必读
mcps/dbx/tools/dbx_execute_query.json      ← 每次会话首次必读
mcps/dbx/tools/dbx_describe_table.json     ← 需要查表结构时读
```

> **路径**：MCP 工具 Schema 位于 IDE 共享缓存目录，每台机器路径不同（勿写死具体盘符），定位方式：用 Glob 搜索 `**/mcps/{server}/tools/{tool}.json` 找到后 Read 即可

#### 连接信息与查询规则

- **连接信息从配置读取**：连接名取配置 `database.connection_name`（dbx 工具的 `connection_name` 参数），数据库名取 `database.database`（`database` 参数）；未配置时调用 `dbx_list_connections` 列出可用连接后向用户确认
- **唯一数据源**：所有测试数据**必须**通过 `dbx` MCP 从数据库获取
- **只读操作**：`dbx` MCP **仅允许执行 SELECT 查询**，**严禁** INSERT / UPDATE / DELETE / DROP / ALTER
- **禁止虚构数据**：用例中的会员名称、门店名称、订单编号、金额等字段，**严禁**凭想象编造
- **bigint精度**：查询含 `bigint` 类型的 ID 字段时，**必须**使用 `CAST(id AS CHAR)` 防止精度丢失
- **临时数据排除**：统计会员数量时，WHERE 条件须加 `temp_user = 0` 排除临时会员
- **租户/账号确认**：编写测试用例前，**先判断需求是否涉及具体业务数据**。若涉及则主动询问用户目标租户（tenantId）及登录账号密码；若为系统配置类或总后台类功能则无需询问

#### 动态选表原则

**禁止固定套用**：根据需求业务领域动态判断需查询的表。通过 `information_schema.TABLES` 同时搜索 **TABLE_NAME**（英文表名模式）和 **TABLE_COMMENT**（中文注释），一次查询即可定位（`{数据库名}` 取配置 `database.database`）：

```sql
SELECT TABLE_NAME, TABLE_COMMENT FROM information_schema.TABLES
WHERE TABLE_SCHEMA = '{数据库名}'
  AND (TABLE_NAME LIKE '%purchase%' OR TABLE_COMMENT LIKE '%采购%')
ORDER BY TABLE_NAME;
```

> **搜索技巧**：
> - `TABLE_NAME` 用英文关键词（`order`、`goods`、`purchase`、`pay`、`head`=门店、`provider`=供应商）
> - `TABLE_COMMENT` 用中文关键词（`%订单%`、`%商品%`、`%采购%`、`%支付%`、`%门店%`）
> - 两个条件用 OR 连接，总能命中

找到目标表后，用 `dbx_describe_table` 查看字段定义；需要样本数据时再用 `dbx_execute_query` 查询。

### 8.2 知识库补充规则（weknora-knowledge MCP）

- **触发时机**：当信息不足以支撑用例编写或业务细节不确定时，**先调用** weknora-knowledge MCP 调查
- **知识库选择**：从 `config/project.config.json` 的 `knowledge_bases` 清单中，按需求所属业务域（如供应链 / 门店 / TAPD历史迭代产品需求）匹配对应 `id` 直接查询
- **⚠️ 注意**：`list_knowledge_bases()` 和 `find_knowledge_base()` 目前会返回空结果，不要依赖它们搜索知识库，直接使用配置中的 ID 调用 `get_knowledge_base` / `list_knowledge` / `find_knowledge`
- **优先级**：Spec（若有）是第一信息源；知识库是补充信息源，两者冲突时以 Spec 为准
- **兜底判断流程**：当遇到不确定的业务规则/字段含义/状态枚举时，按以下顺序逐级查证：
  1. 查 TAPD 需求描述原文（`get_stories_or_tasks` 的 `description` 字段）
  2. 查 Spec 文档（若有）
  3. 查知识库（按业务模块选择对应 ID）
  4. 查 dbx 数据库表结构/注释（`dbx_describe_table`）
  5. 以上均无法确认的，标记为待确认项抛给用户确认
- **禁止跳过**：可通过上述途径解决的信息缺失不得跳过或臆测，必须完成自纠后再生成用例

### 8.3 需求图片获取与 OCR 提取规则

- **触发时机**：TAPD 需求描述中包含 `<img>` 图片时，编写用例前**必须先**获取图片中的文字内容
- **获取图片**：调用 `get_image` 工具，传入 `workspace_id` 和 `image_path`，返回 `download_url`
- **📌 保存到缓存目录（重要）**：拿到 `download_url` 后，**必须**保存到 `workspace/personal/image-cache/{需求ID}/` 目录下，禁止直接保存到项目根目录或其他位置：
  1. 先创建目录：`mkdir workspace/personal/image-cache/{需求ID}/`（不存在则自动创建）
  2. **统一用 `download_images.js` 下载**：将 `[{"url":"{download_url}","out":"{缓存目录}/{原始文件名}"}, ...]` 写入临时参数文件，执行 `node .qoder/skills/testcase-reviewer/scripts/download_images.js {参数文件}`，下载成功后删除参数文件（脚本会自动写入/更新缓存目录 `.manifest.json`，记录 md5/size/cached_at，供 testcase-reviewer 一致性校验使用）
- **链接时效**：`get_image` 返回的 `download_url` 有效期为 300 秒（5 分钟），需及时下载；失败时重新调用 `get_image` 刷新链接后重试
- **图片缓存保留**（重要）：用例生成完成后**默认保留** `workspace/personal/image-cache/{需求ID}/` 下的图片，供后续核查复用（与 testcase-reviewer 缓存策略一致：**testcase-reviewer 核查时按 TAPD `<img>` 同名匹配优先复用该缓存目录，复用前通过 `.manifest.json` + 实时图 Content-Length 校验一致性**，无需重新下载；因此下载时**必须用 TAPD 原始文件名命名**，禁止自定义重命名，否则无法复用）。缓存截图随仓库入库，**提交前人工检查是否含敏感内容**；若确需释放空间：`Remove-Item "workspace/personal/image-cache/{需求ID}/" -Recurse -Force -ErrorAction SilentlyContinue` 或要求 AI 清理
- **识图：调用 `/ocr` skill**（统一入口，不直接调用脚本）：图片就绪后，**调用 `/ocr` skill**（参数：图片路径），由 /ocr 完成三轨协同识图（Windows OCR 覆盖率 + OpenOCR 精读排序 + Read 结构理解）、交叉验证、置信度追踪与兜底处理，直接使用其返回的三通道融合结果：
  1. **融合文本**：Windows OCR 全量文字（含 `fixes` / `suspicious` 标记）+ OpenOCR 排序文本（含 `score` 置信度）
  2. **UI 结构描述**：Read 输出的按钮/弹窗/表单/下拉/颜色标记等结构信息
  3. **专项处理由 /ocr 负责**：浅灰小字、双色标注通读、大图 bbox 相对坐标、GLM 第二意见（含未配置自动降级）、人工切图兜底等细节见 `.qoder/skills/ocr/SKILL.md`，本 skill 不再重复实现
  4. **三通道交叉验证**：同区域文本互相印证，错别字在对比中暴露（如 Windows OCR 的"默 / 认" vs OpenOCR 的"默认"）
- **📊 OCR 置信度追踪（重要）**：从 `/ocr` skill 返回的文本块数据中解析每个块的 `score` 字段（0~1 置信度），**必须**执行：
  1. **提取并记录每张图片的所有文本块及对应 `score`**
  2. **标记置信度 < 0.7 的文本块**为「低可信度文本块」，这些区域的识别结果**不可靠**，不能直接作为用例编写依据
  3. 遇到低可信度文本块时，按以下优先级获取正确信息：
     - 🥇 **查 Windows OCR 同区域文本**：Windows OCR 对不同区域的识别精度可能不同，同区域文本可交叉验证
     - 🥇 **查 TAPD 需求描述原文**（`get_stories_or_tasks` 返回的 `description` 字段）
     - 🥇 **查 Spec 文档**（若有）
     - 🥉 **用 Read 工具复核图片**，但 Read 的描述必须与上述原文交叉校验
  4. **禁止**将低可信度 OCR 文本直接作为用例预期结果/文案的依据，必须找到原文确认
- **🎨 颜色标记识别（彩色标记+删除线识别，重要）**：需求图片（尤其是注释面板）中的文字可能以多种颜色出现，**颜色语义从配置 `color_legend` 读取（各团队可自定义，未配置时用默认图例），默认图例：红色=本次迭代修改（核心变更点）、紫色=开发中临时改动、橙色=未实现或他人并行修改（须先验证范围）、黑色=原始逻辑/纯新增**。红色/紫色及蓝/绿等其他可区分彩色为需求正相关内容（用例核心依据），橙色须以 TAPD 描述/开发评论确认范围，黑色/灰色背景文字多为上下文参考。涉及删除线的文字表示功能移除。详细规则见 `.qoder/skills/ocr/SKILL.md`「颜色标记识别规则（彩色标记+删除线识别）」，本处为要点：
  1. **彩色标记识别**：图片中有颜色标记的文本（红/紫/橙/蓝/绿等任何与背景色可区分的彩色）均视为「需求正相关文本」，须编写用例覆盖（橙色标记须先以 TAPD 描述/开发评论确认属于本次需求范围；紫色标记为开发中临时改动，与 TAPD 描述冲突时以 TAPD 描述为准）。颜色用于识别变更点区域，而非限制用例范围
  2. **全黑图片兜底**：若图片中所有文字均为黑色（无任何彩色标记），推断该功能为全新功能（非存量功能变更），应**基于所有注释文本内容编写用例**
  3. **删除线文本处理**：OCR 识别到带删除线（~~文本~~）的文字，说明该功能被移除/下线，**不得为其编写用例**。若删除线文本旁存在无删除线的替换文本，用例以替换文本为准
  4. **黑色/灰色辅助说明**：操作流程说明、示例数据、面板标题、通用说明等纯辅助性文字（无业务规则含义）仍为「上下文参考」，仅用于理解语境，不独立编写用例
  5. **无法区分颜色的处理**：若 /ocr 无法精确判断文本颜色，结合 TAPD 需求描述原文 + Read 结构描述综合推断，仍无法判断时标记为待确认项抛给用户确认
  6. **黑/灰文字中的业务规则例外**：黑色/灰色文字中若包含字段枚举值、状态值、选项清单等确属需求的业务规则，即使无彩色标记也应编写用例——但此项须以 TAPD 描述/开发评论中有依据为前提
  7. **交叉核对**：黄色/彩色标注注释可能与灰色说明文字冲突（如默认值、文案差异），读取用于交叉验证；冲突时以 TAPD 描述为准并标记待确认项
- **⚠️ 原型图使用原则**：OCR 提取文字内容（规则说明、字段名称、提示文案、数值），Read 分析 UI 结构（按钮/弹窗/表单/表格等交互元素）；UI 颜色、弹性样式等视觉细节不作为预期依据
- **🔍 原型图注释/标注文本范围核实（重要）**：原型图片的右侧或上方常包含独立的**注释/标注面板**（如 "样式调整""取值调整""交互说明" 等区块），AI 需注意：
  1. 注释面板中的文本**可能同时包含**需求范围内的变更点（如 tab 切换）和范围外的 UI 设计细节（如按钮颜色、鼠标手型、文案措辞调整）
  2. **必须**以 TAPD 需求标题/描述（`get_stories_or_tasks` 返回的 `name` 和 `description`）为权威依据，逐条判断每条注释是否属于需求范围
  3. 需求范围中明确提及的 → 生成用例；**仅存在于注释面板中、需求范围未提及的 UI 细节 → 不得生成用例**
  4. 不确定的注释 → 标记为待确认项并提示用户
- **🚫 禁止调用浏览器查看原型链接**：TAPD 需求描述中附带的原型链接（如 modao.cc 等在线设计工具链接）**不得**通过浏览器打开查看。原型设计内容以需求描述中直接贴出（`<img>` 标签）的图片为准

> **说明**：识图流程由 AI 自动调用 `/ocr` skill 完成，用户无需手动调用 `/ocr` 命令。若 OCR 无法有效提取文字，/ocr 会提示人工切图。

### 执行顺序建议

#### 单需求模式

1. **获取需求信息**：通过 TAPD 获取需求描述（有 Spec 文档则优先以 Spec 为准）
2. **调用 `/ocr` skill 识图**：若需求描述中包含 `<img>` 图片，调用 `get_image` 获取 `download_url`，**优先下载到 `workspace/personal/image-cache/{需求ID}/`**，然后**调用 `/ocr` skill**（参数：图片路径）完成三轨协同识图：
   - **获取融合结果**：三通道融合文本 + UI 结构描述 + 每个文本块的 `score` 置信度
   - **低可信度文本标注**：标记 `score < 0.7` 的文本块，这些内容**不可直接使用**，需查 Windows OCR 同区域文本或 TAPD 需求原文确认
   - **颜色标记识别（彩色标记+删除线识别）**：结合 /ocr 返回的 Read 结构描述，**判断哪些文字带有颜色标记**（红/紫/橙/蓝/绿等；语义按配置 `color_legend` 解释，默认：红=本次修改、紫=开发中临时改动、橙=未实现或他人并行修改、黑=原始逻辑/纯新增），红色/紫色为需求正相关内容（橙色先验证范围）；图片全黑色时推断为新功能，基于全部注释文本编写用例。**注意识别删除线文本，有删除线的功能已移除不得编写用例**
   - **旧功能排除检查**：对原型图中的每个 UI 元素，确认它是否是本次需求的变更点（有彩色标记即变更点）。**非变更点的旧 UI 元素不得生成测试用例**。例外：图片全黑色（无彩色标记）时推断为新功能，所有 UI 元素均视为变更点，不受本条限制
   - **三通道交叉验证**：Windows OCR 文字 vs OpenOCR 文字 vs Read 结构描述，同区域文本互相印证，发现遗漏和错别字
   - 若 OCR 识别效果不佳，/ocr 会提示人工切图，按提示引导用户切图后重新提供
   - 注意：需求描述中附带的原型链接（如 modao.cc）禁止调用浏览器查看，以 `<img>` 图片内容为准
3. **标记信息缺失点**：结合需求描述 + OCR 文案 + Read 结构描述，识别信息不足处，调用 weknora-knowledge MCP 查询补充
4. **获取测试数据**：若涉及具体业务数据，确认租户后调用 dbx MCP 获取真实测试数据
5. **生成测试用例**：基于完整信息生成测试用例
6. **保留图片缓存**：图片默认保留在 `workspace/personal/image-cache/{需求ID}/`（供后续 testcase-reviewer 核查复用，避免重复下载）；如需释放磁盘空间可手动删除该目录或要求 AI 清理

#### 多需求串行模式

收到多个需求 ID 时，按以下流程**逐个串行**处理：

1. **解析所有需求 ID**：识别并列出用户输入的所有需求 ID，确定处理顺序（按输入顺序）
2. **逐个需求完整循环**：对每个需求依次执行：
   - 单需求获取 TAPD 信息（名称、描述、迭代、图片路径）
   - 下载图片到缓存目录
   - 调用 `/ocr` skill 识图（多张图片逐张调用）
   - 需求分析（第一~第五步）
   - 生成测试用例（第六~第七步）
   - 自检（第十步）
   - 双路径归档
   - 输出单个需求进度报告
   - **遇阻塞**：标记 ⏭️ 跳过，记入阻塞清单（原因 + 建议解决方式），**立即继续下一个需求**，不中断批次（详见「阻塞处理与人工介入」）
3. **全部生成后逐审查**：所有需求的用例文件都生成并归档后，**逐个调用 testcase-reviewer skill 进行用例核查**（阻塞跳过的需求不核查；**无图片的需求通知 testcase-reviewer 跳过 OCR 阶段，直接进入文本级比对**）。**核查按「有据直接修正」模式自动完成修正**：证据链完整、结论唯一的差异（原型注释双通道验证 score≥0.7、TAPD 描述原文、开发评论接口说明）直接双路径修正并同步矩阵，**无需用户人工再执行 review**；仅依据不足/歧义项抛待确认等用户确认
4. **全部核查完成后**：输出全量汇总报告（**含需人工介入清单**）

> **注意**：每个需求独立走完完整生命周期，不与其他需求并发。这意味着 TAPD 获取、图片下载、OCR 识图、用例生成、归档都在同一个处理周期内完成。

## 第九步：OCR 原文反查校验（Review）

生成测试用例后，**必须**执行 OCR 原文反查校验，确保用例与需求原文一致：

### 校验方法

1. **逐条比对**：拿着 OCR 提取的原文（或 Spec 原文），逐一核对每条用例：
   - 用例中的**变更点/业务规则**是否在 OCR 原文中有明确依据？
   - 用例中的**预期结果/提示文案**是否与原文一致，有无曲解？
   - 用例中的**数值/状态/条件**是否与原文完全匹配？
   - 是否有原文中明确提到的规则未被任何用例覆盖？

2. **遗漏检查**：将 OCR 原文的每个要点标记为 ✅（已覆盖）或 ❌（未覆盖），确保原文无遗漏

3. **关联引用可追溯**：每条用例的「关联引用」列应能对应到 OCR 原文的某个具体段落/编号

### 发现问题的处理方式

| 问题类型 | 处理方式 |
|:---|:---|
| 遗漏未覆盖的业务规则 | 补充对应用例 |
| 预期结果与原文不符 | 修正预期结果 |
| 文案/数值/状态名错误 | 修正错误信息 |
| 自主臆测的额外内容 | 删除臆测用例 |

### 兜底情况

若 OCR 原文质量不佳（识别结果不完整、文字错乱严重），无法作为可靠的校验依据时：
- 若有 Spec 文档，改用 Spec 原文进行反查校验
- 若既无可靠 OCR 也无 Spec，提示用户人工复核重点用例

### OCR 置信度报告生成（新增）

生成测试用例后，若存在 `score < 0.7` 的低可信度文本块，**必须**在本次对话末尾输出 OCR 置信度报告，供用户参考排查。

> **⚠️ 禁止**：禁止将置信度报告的任何内容写入测试用例文件（`{需求ID}-{需求标题}.md`）中，也禁止写入独立的报告文件。

**输出方式**：在对话末尾以 Markdown 格式直接输出，不写入任何文件。

**报告内容**：

```
## OCR 置信度报告

| 序号 | 图片文件 | OCR原文（低可信度） | 置信度 | 通道来源 | 可能影响的用例 | 说明 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | xxx.png | 默认仓库 | 0.32 | OpenOCR | ①「入库默认仓库校验」 | 内容不可靠，需用户确认 |
| 2 | xxx.png | 缓荐 | - | Windows OCR | ②「缓存清空操作」 | 与 OpenOCR 同区域文本"缓存"冲突，需确认 |
```

**生成方法**：
1. 回顾 `/ocr` skill 返回的结果，提取 `score < 0.7` 的所有文本块（OpenOCR），以及 Windows OCR 中与 OpenOCR 高可信文本冲突的文本行
2. 对每个低可信度文本块，分析其内容可能影响的用例：
   - 将 OCR 原文关键词与测试用例中的「预期结果」「操作步骤」「前置条件」进行语义匹配
   - 如果某用例的内容依赖了该低可信度区域的文本信息，标记为「可能影响」
3. 在报告末尾添加说明：
   > ⚠️ 以上 OCR 识别结果置信度低于 0.7，内容可能不准确。请用户逐条核对，确认无误或提供修正内容。

**报告交付用户后，等待用户反馈**：
- 用户确认无误 → 保留当前用例
- 用户提供纯文本修正 → 按用户提供的文本更新对应用例

## 第十步：自检与经验沉淀

### 两模式自检清单

用例生成完毕后，根据是否有 Spec 自动聚焦对应项，逐项审视：

#### Spec 模式（有 Spec 时必检）

| 自检项 | 说明 |
| :--- | :--- |
| □ AC-xx 覆盖 | 每条验收标准至少生成 1 条正向验证用例 |
| □ Rxx 规则覆盖 | 每条业务规则至少覆盖 1 条校验用例，复杂规则有组合用例 |
| □ 状态枚举覆盖 | 每个状态值都有正向流转 + 逆向/异常流转用例 |
| □ 触发条件覆盖 | 布尔表达式的 true/false 分支都覆盖了 |
| □ 异常处理一致性 | 异常处理表中每条场景的文案和用户提示与 Spec 完全一致 |
| □ 范围外确认 | 范围外清单（X01-Xxx）未越界生成用例 |

#### 普通模式（无 Spec 时必检）

| 自检项 | 说明 |
| :--- | :--- |
| □ OCR 文本全覆盖 | OCR 提取的每条文案（规则说明/字段名称/提示文案/数值等）都有用例覆盖 |
| □ 彩色标记识别 | 确认已按配置 color_legend 图例语义（默认：红=本次修改/紫=开发中临时改动/橙=未实现或他人并行修改/黑=原始逻辑）正确区分需求正相关文本与辅助说明文本，无遗漏/无过度 |
| □ 删除线识别 | 图片中带删除线的文本已识别并排除，未为其编写用例 |
| □ 用例维度覆盖 | 平铺表用例已按排序规则（正向→规则→交互→边界→异常→防抖→数据一致性）排列，各维度均有覆盖 |
| □ 变更点无遗漏 | 所有变更点已编号（①②③...）且每条都有对应用例 |
| □ OCR 原文逐条过 | OCR 原文的每个要点标记 ✅/❌，❌ 的已补齐 |
| □ AI 臆测排查 | 无原文未提及、纯属 AI 臆想的用例，有则删除 |
| □ 文案数值一致 | 预期结果/提示文案/数值/状态名与 OCR 原文完全匹配 |

#### 通用自检项（两模式共用）

| 自检项 | 说明 |
| :--- | :--- |
| □ 可独立阅读 | 前置条件/操作步骤/预期结果无跳转引用（"见 xxx"、"同上"） |
| □ 数据真实性 | 门店名/会员名/订单号/金额来自 dbx 真实查询，非虚构 |
| □ 按钮防抖 | 所有涉及按钮操作的场景已补充防抖用例 |
| □ 覆盖矩阵校验 | 各维度用例数量之和 = 实际表格条数 |
| □ 无技术术语 | 用例描述无数据库字段名、接口参数名、SQL 等技术标识符 |
| □ 旧功能排除 | 原型图中的旧 UI 元素（非本次需求变更点）未生成测试用例（全黑图片推断为新功能时不受本条限制） |
| □ 低置信度OCR处理 | OCR 识别置信度 < 0.7 的文本块已通过 Windows OCR 同区域文本或 TAPD 需求原文确认正确信息，未直接使用 |
| □ 知识库已查询 | 不确定的业务细节已通过对应知识库查询补充，未凭臆测编写 |

### 经验沉淀

若发现具备通用性的问题类型（如某类规则易遗漏、某类文案易曲解等），**自主决定**是否沉淀到 `SKILL.md` 并用 `UpdateMemory` 记录经验，使后续调用自动规避。

## 核心禁止规则（务必遵守）

1. **禁止虚构数据**：所有测试数据必须通过 dbx MCP 真实查询获取
2. **禁止跳转引用**：前置条件/操作步骤/预期结果中不得写「见 xxx」「同上」等
3. **禁止交互臆测**：对 Spec 或需求描述中未明确说明的交互行为，严禁主观臆测
4. **禁止数据行为猜测**：字段取值范围、是否为空、空值显示样式等不得主观猜测
5. **禁止原型UI视觉细节作为预期依据**：OCR 提取文案、Read 识别 UI 结构元素（按钮/弹窗/表单等）均可用于用例编写；但 UI 颜色、样式、布局尺寸等视觉设计**不代表最终实现**，不得以此作为预期结果的判断依据
6. **按钮防抖必测**：涉及按钮操作的需求，必须补充防抖测试用例
7. **禁止调用浏览器查看原型链接**：TAPD 需求描述中的原型在线链接（如 modao.cc）不得通过浏览器打开查看，原型内容以 `<img>` 图片为准
8. **按彩色标记规则识别需求正相关内容**：需求图片中颜色语义从配置 `color_legend` 读取（各团队可自定义；默认图例：**红色**=本次迭代修改、**紫色**=开发中临时改动、**橙色**=未实现或他人并行修改、**黑色**=原始逻辑/纯新增）。红/紫及蓝/绿等其他可区分彩色为需求正相关，须编写用例覆盖；橙色须先以 TAPD 描述交叉验证范围；图片全黑色时推断为新功能，基于全部注释文本编写用例。黑色/灰色背景文字中的操作流程说明、示例数据等辅助内容仅用于理解语境，不独立编写用例。详见 8.3 节「颜色标记识别」完整规则
9. **禁止技术术语**：前置条件、操作步骤、预期结果中的描述**必须使用自然语言**，禁止出现数据库字段名（如 `production_date`）、接口参数名（如 `tenantId`）、SQL 语句等技术标识符
10. **⚠️ 禁止将原型图注释/标注文本直接等同于需求范围**：原型图片的右侧/上方的**注释/标注面板**中，常包含 "样式调整""取值调整""交互说明" 等辅助性文本，这些文本中可能同时包含**本次需求变更点**（如 tab 切换）和**非需求内容**（如按钮颜色、鼠标手型、文案措辞微调等 UI 细节）。AI 须严格以 **TAPD 需求标题/描述**（`get_stories_or_tasks` 返回的 `name` 和 `description`）作为需求范围的权威依据，对原型图注释文本中的每条内容逐一判断：
    - **在需求范围中明确提及** → 生成对应用例
    - **在需求范围中未提及**（仅存在于原型注释中，属于 UI 设计细节）→ **不得生成测试用例**
    - 若不确定某项注释是否属于需求范围，标记为待确认项并提示用户确认
    - **例外**：若图片仅含黑色文字（无彩色标记），推断为新功能，不受本条限制，应基于注释文本全部内容编写用例
11. **删除线文本不作为用例依据**：OCR 识别到的删除线文本（~~文本~~）表示功能已移除/下线，不得为其编写用例。替换的新文本按正常规则处理

> **总结**：测试用例编写**只涉及需求功能逻辑**，**不涉及交互UI设计**。需求中的 UI 交互以最终 UI/UX 设计稿为准，用例阶段不做 UI 细节验证。

## 进度自检清单（多需求专属）

在完成所有需求后，除第十步的通用自检项外，增加以下多需求自检项：

| 自检项 | 说明 |
| :--- | :--- |
| □ 需求无遗漏 | 汇总报告中的需求清单与用户输入的 ID 列表完全一致，无遗漏/重复 |
| □ 中断恢复 | 若对话中途中断，能从最近完成的需求继续（用户重新输入未完成的 ID 即可） |
| □ 跨需求去重 | 不在多个需求之间为同一功能点的同一规则编写重复用例（如通用权限校验只需在一个需求中覆盖） |
| □ 跨需求一致性 | 同一功能点在不同需求中表述的规则/文案/状态名保持一致 |
| □ 阻塞需求全部抛出 | 阻塞清单中的每个需求都已在汇总报告「需人工介入清单」列出（含阻塞环节、原因、建议），无遗漏 |
| □ 图片缓存管理 | 所有需求的图片缓存已按策略保留或清理 |
| □ testcase-reviewer 全覆盖 | 每个成功生成的需求用例文件都已执行 testcase-reviewer 核查并确认通过（阻塞跳过的需求不在此列） |
