# Image OCR - 三轨协同识图（Windows OCR + OpenOCR + VLM/Read）

## 调用方式

- **独立调用**：`/ocr <图片路径>`（输出三通道交叉验证结果）
- **被其他 skill 调用**：mcpcase / case-review 等 skill 通过 Skill 工具以**图片路径**为参数调用本 skill，由本 skill 完成三轨协同识图、置信度追踪与兜底处理；调用方直接使用本 skill 输出的三通道融合文本、UI 结构描述与置信度数据，**无需重复实现脚本调用**
- **参数**：图片路径（支持中文路径）

> 调用方职责：只需传入图片路径；三通道脚本选择、交叉验证、低可信度处理、人工切图兜底等全部由本 skill 内部完成。

## 概述

### 痛点来源

| 痛点 | 描述 | 实测数据 |
|:---|:---|:---|
| 单一引擎覆盖率不足 | OpenOCR 文本块级检测，对复杂 UI 截图漏检 | Windows OCR 可提取 628 行，而 OpenOCR 仅几十~两百块 |
| 排序错乱 | Windows OCR 按检测顺序排列，文字顺序受布局影响 | "默认"变"默 / 认"，跨列文本交叉混合 |
| 错别字 | 像素级引擎对干扰背景/小字识别失真 | "缓存"→"缓荐"，"蓝牙"→"蓝呀"，"公斤"→"公 fi" |
| 无结构理解 | 纯 OCR 只认文字，不认按钮/弹窗/表格布局 | 需结合 Read/VLM 分析 UI 结构 |

### 三通道分工

| 通道 | 脚本/工具 | 负责 | 不负责 | 解决痛点 |
|:---|:---|:---|:---|:---|
| **Windows OCR**（覆盖率） | `windows-ocr.ps1` | 全量文本提取，不漏小字/装饰区域内的文字；内置词典纠错与可疑行标记 | 几何排序（PS5.1 下 bbox 不可用）、结构理解 | OpenOCR 漏检 |
| **OpenOCR**（精读排序） | `ocr_extract.py` | 排序自然、置信度打分、多列裁剪、大图切块 | 覆盖率不如 Windows OCR | Windows OCR 排序乱、错别字 |
| **VLM/Read**（结构） | `Read` 工具 | 理解 UI 布局、区分按钮/弹窗/表格、识别颜色标记 | 精确提取小字文案、长段数值 | 纯 OCR 不懂结构 |

### 三通道互补关系

```
Windows OCR 的覆盖率 × OpenOCR 的排序精度 × VLM 的结构理解 = 完整识图能力
        ↑                        ↑                        ↑
    不漏字                    排对序                    懂结构
```

## 通道 1：Windows OCR（覆盖率通道）

### 脚本位置
`.qoder/skills/ocr/scripts/windows-ocr.ps1`（与 vlm-vision.ps1 同目录）

### 使用方式

```powershell
# 在项目根目录下执行（勿写死绝对路径，各成员 clone 位置不同）
cd .qoder\skills\ocr\scripts

# 基本用法（输出 JSON）
powershell .\windows-ocr.ps1 -ImagePath "需求图.png"

# 保存到文件
powershell .\windows-ocr.ps1 -ImagePath "需求图.png" -Output result.json

# 完全关闭内置后处理（兜底旧行为）
powershell .\windows-ocr.ps1 -ImagePath "需求图.png" -NoSort -NoMerge -NoFix -NoMark
```

> 内置后处理（默认全部开启）：① 自适应排序（列检测+行分组+行内 x 排序）；② 同行碎片合并；③ 历史错别字词典纠错（fixes 记录替换痕迹）；④ 可疑行标记（suspicious，仅提示不改文）。PowerShell 5.1 下 Windows.Media.Ocr 的 BoundingRect 投影为 null，脚本自动探测并降级排序/合并（输出 `geometry: "unavailable"`），排序职责由 OpenOCR 通道承担。

### 输出格式

```json
{"text": "识别出的全部文字（已纠错、已按可用几何信息排序）...", "blocks_count": 628, "blocks": [{"transcription": "文字行", "bbox": {"x1": 10, "y1": 20, "x2": 100, "y2": 40}}, ...], "sorted": true, "fixes": [{"from": "缓荐", "to": "缓存", "count": 1}], "merged": 2, "suspicious": [{"text": "公fi", "reason": "中英混排疑似乱码"}], "fallback": false, "geometry": "ok"}
```

| 字段 | 说明 |
|:---|:---|
| `text` / `blocks` / `blocks_count` | 与原版兼容；text 为后处理后的全文 |
| `sorted` | 是否应用了内置排序（bbox 可用时才有意义） |
| `fixes` | 词典纠错替换痕迹（from → to → count），供追溯 |
| `merged` | 同行碎片合并的对数 |
| `suspicious` | 启发式标记的疑似乱码行（仅提示，未改文） |
| `fallback` | 后处理异常时是否回退引擎原始输出 |
| `geometry` | `ok` = bbox 可用（排序/合并生效）；`unavailable` = PS5.1 投影缺陷 bbox 为 0，排序/合并自动跳过，排序以 OpenOCR 为准 |

### 特点

| 特性 | 说明 |
|:---|:---|
| 覆盖率 | 极高，逐像素检测，不遗漏任何可见文字区域 |
| 实测 | 复杂多面板 UI 截图可达 600+ 行，远超 OpenOCR |
| 速度 | 毫秒级（本地离线，无需网络） |
| 排序 | 内置自适应排序（列检测+行分组+行内 x 排序）；bbox 可用时自动生效，PS5.1 下不可用自动降级（geometry: unavailable） |
| 纠错 | 内置历史错别字词典自动替换（fixes 记录痕迹）+ 可疑行启发式标记（suspicious 仅提示） |
| 适用场景 | 复杂 UI 截图、多面板混合图、流程图、小字密布图 |

### 已知限制
- 仅支持 Windows 10+（依赖 Windows.Media.Ocr API）
- 对倾斜文字、手写体识别精度下降
- **PS5.1 下 BoundingRect 投影为 null**：blocks.bbox 恒为 0（无效数据，历史版本一直如此），脚本自动探测后跳过排序/合并（输出 `geometry: "unavailable"`），排序以 OpenOCR 通道为准；若未来环境 bbox 可用（如 PowerShell 7 CsWinRT 投影），排序/合并自动生效，无需改调用方
- 无置信度打分字段（置信度由 OpenOCR 通道提供）

### 词典维护规范（持续改进闭环）

`$script:typoDict`（windows-ocr.ps1 内）是历史错别字映射表，使用中发现新错别字时**必须**按以下规范维护（保持词典持续有效、防止无限膨胀）：

1. **发现**：识图流程中，`suspicious` 标记行、三通道交叉验证暴露的**稳定错别字**（同一错字重复出现 ≥2 次，或与 OpenOCR/Read 交叉确认）→ 如"胸物车"→"购物车"、"按im去重"→"按item去重"（2026-08-10 实测新增）
2. **更新**：修改 `$script:typoDict` 增加映射（key 为引擎常见原始形态，含空格/斜杠变体）；同义高频错（如"默 / 认""默/认"）可多条并存
3. **转码**：修改含中文的 .ps1 后**必须重新转码 UTF-8 with BOM**（PowerShell 5.1 按 ANSI 解析中文报错），再执行验证
4. **验证**：对出现错别字的原图重跑 `windows-ocr.ps1`，确认输出 `fixes` 字段命中对应条目、`fallback=False`
5. **上限**：词典条目**上限 50 条**；接近/超过上限时，优先移除"近期从未命中且与当前业务场景无关"的历史条目（如早期项目特有词），保留近期验证命中的条目；每条新增/淘汰在团队记忆库 `02-ocr-pipeline.md` 词典维护记录中注明
6. **不收录**：**字面映射固定**才入词典（如"按im去重"→"按item去重"，每次出现都同形）；依赖上下文才能判断的语义级替换（如"规格"误识为"im"但该形态可能对应多个正确词）、价格符号类（¥→Y 后随数字变化无固定串）不强行入词典，由 suspicious 标记 + 交叉验证兜底

## 通道 2：OpenOCR（精读排序通道）

### 脚本位置
`.qoder/skills/ocr/scripts/ocr_extract.py`（与 windows-ocr.ps1 / vlm-vision.ps1 同目录）

### 使用方式

```powershell
# 在项目根目录下执行（勿写死绝对路径）
cd .qoder\skills\ocr\scripts

# 基本用法（拼接文本，兼容旧行为）
python ocr_extract.py "需求图.png"

# 🆕 输出完整块信息（含 score 和 bbox）
python ocr_extract.py "需求图.png" --json-blocks

# 🆕 仅输出高置信度文本块（过滤低可信度噪声）
python ocr_extract.py "需求图.png" --json-blocks --min-score 0.7

# 超大图自动切块
python ocr_extract.py "需求图.png" --split --json-blocks

# 保存到文件
python ocr_extract.py "需求图.png" --json-blocks -o blocks.json
```

### 输出格式

**默认模式（兼容旧行为）：**
```json
{"text": "识别出的纯文本内容...", "blocks_count": 121}
```

**`--json-blocks` 模式（新）：**
```json
{
  "blocks_count": 121,
  "blocks": [
    {
      "transcription": "选择入库类型交互说明",
      "score": 0.95,
      "bbox": {"x1": 50, "y1": 30, "x2": 300, "y2": 50}
    },
    {
      "transcription": "默认仓库",
      "score": 0.32,
      "bbox": {"x1": 50, "y1": 55, "x2": 150, "y2": 70}
    }
  ]
}
```

### 特点

| 特性 | 说明 |
|:---|:---|
| 排序 | 自适应排序（`sort_blocks_adaptive`）：列检测→行分组→同行按 x 排序，顺序自然 |
| 置信度 | 每个文本块附带 `score` 字段（0~1），`< 0.7` 为低可信度 |
| 多列裁剪 | 自动检测并裁剪左右列布局，每列独立识别后按列拼接 |
| 大图切块 | `--split` 参数，>2000px 自动切块，相邻块重叠 120px |
| 速度 | 每张图约 8~10 秒（mobile 模型），大图切块后 N 块 × 8~10 秒 |

### 智能决策逻辑

1. 第一次 OCR 检测文本位置
2. 分析文本块 x 坐标分布，判断是否有多列
3. 如果列数 ≤1 → 直接复用第一次结果（1 次 OCR，无额外开销）
4. 如果列数 2~3 → 裁剪后每列独立识别（排序更准）
5. 如果列数 >3 或列宽 <30px → 自动回退到单列模式（兜底）

### 完整参数说明

| 参数 | 说明 |
|:---|:---|
| `image_path` | 图片路径（必填，支持中文路径，自动处理） |
| `--split` | 可选，对超大图片（>2000px）自动切块 |
| `--no-crop` | 可选，禁用自动多区域检测裁剪（使用全局识别+排序，旧行为） |
| `--output` / `-o` | 可选，将结果保存到文件 |
| `--json-blocks` | 🆕 输出每个文本块的完整信息（含 score 和 bbox），而非仅拼接文本 |
| `--min-score` | 🆕 仅输出置信度 >= 此值的文本块（默认 0.0 即全部输出） |

### 安装依赖

如果 `python ocr_extract.py` 时报找不到 openocr 模块，会**自动安装**。也可手动安装：
```bash
pip install openocr-python
```
首次运行会自动下载模型（~37MB，仅一次），缓存到 `%USERPROFILE%\.cache\openocr\`。

### 排序算法说明

`sort_blocks_adaptive()` 动态计算文本块的中位高度作为行高基准，自适应分组粒度替代旧版固定 `round(y/30)` 分组。同时通过 x 坐标 gap 发现列边界，将来自不同列（如左面板和右侧标注框）的文本先按列分开再排序，避免跨列混合。

## 通道 3：VLM / Read（结构通道）

### 通道选择：Read 为主，GLM 为第二意见

结构通道以 **Read 工具为主**，GLM（云端 VLM）作为 **Read 结果不完整时的第二意见（交叉验证），而非替代**。

实测对比结论（2026-08-06，需求 1019343 入库管理原型图）：

| 维度 | Read（首选） | GLM（glm-4v-flash） |
|:---|:---|:---|
| 响应 | 秒级，本地无依赖 | ~13s，需 GLM_API_KEY + 网络 |
| 输出 | 自然语言详细描述 | 结构化 Markdown 分节 |
| 细节保真 | ✅ 表格数值/规则全文/单据信息完整 | ⚠️ 小字/数字/长段规则易丢失（漏商品行、单价张冠李戴） |
| 幻觉风险 | 无明显幻觉 | 有幻觉风险（行数/数值不准） |
| 适用 | 结构通道默认实现 | 布局概览快查、与 Read 结果交叉验证 |

**GLM 调用方式**（仅当需要第二意见时）：

```powershell
# ① 从用户环境变量读取 GLM_API_KEY 并注入（User scope，非进程变量）
$env:GLM_API_KEY = [Environment]::GetEnvironmentVariable("GLM_API_KEY", "User")
# ② 调用 ocr skill 内置的 vlm-vision 脚本（脚本路径：.qoder/skills/ocr/scripts/vlm-vision.ps1）
powershell .qoder\skills\ocr\scripts\vlm-vision.ps1 -ImagePath "图片路径" -Prompt "请分析该图片的 UI 结构…" -Channel glm -Json -NoCache
```

> ⚠️ 含中文的 .ps1 脚本文件必须保存为 UTF-8 with BOM，否则 PowerShell 5.1 按 ANSI 解析中文报错。

### GLM 未配置时：自动降级 + 配置引导

**检测**：`[Environment]::GetEnvironmentVariable("GLM_API_KEY", "User")` 为空即视为未配置。

**自动降级**：跳过 GLM 通道，结构通道仅用 Read 完成分析（不影响结果正确性），**不得因缺少 GLM 阻塞流程**。

**配置引导提醒**（在对话中输出以下模板，供用户点击跳转）：

```

如需启用 GLM 作为结构通道第二意见（可选，免费）：
1. 注册/登录智谱 AI 开放平台：https://bigmodel.cn/

   - 手动：系统设置 → 环境变量 → 用户变量 → 新建 GLM_API_KEY，重启终端生效

https://docs.bigmodel.cn/cn/guide/models/free/glm-4v-flash），无需付费即可调用。
```

### 使用方式

通过 `Read` 工具分析图片 UI 结构：

```python
Read(file_path="图片路径")
```

### 分析内容

- 按钮位置与文案
- 弹窗层级与内容
- 表格列头与行数据关系
- 下拉选项与输入框
- 标签页切换
- 颜色标记区域（红色变更点 vs 背景文字）
- 注释面板与主图区域的关系

### 交叉验证方法

Read 分析完 UI 结构后，与 OCR 结果做对比；若 Read 输出不完整或对结构存疑，可调用 GLM 作为第二意见，对比两者的结构描述（布局分区、弹窗内容、表格行列）是否一致，不一致处以 Read 为准并结合 OCR 文案核实：

1. **结构 vs 文案对应**：Read 说"有一个确认按钮"，OCR 结果中应有"确认"二字
2. **字段名 vs 取值**：Read 说"表格有'单价'列"，OCR 结果中应有单价对应的数值行
3. **弹窗内容完整性**：Read 说"弹窗内有三个选项"，OCR 应提取到三个选项的文案
4. **遗漏发现**：Read 发现一个 OCR 未提取到的文本区域 → 对该区域单独 OCR/Windows OCR

> **注意**：Read 的图片分析是概括性的，不能替代 OCR 的精确文字提取。两条能力是互补而非替代关系。

## 三通道交叉校验

### 核心思路

同区域文本互相印证，错别字在对比中暴露：

```
场景：图片中有 "默认仓库" 四个字

Windows OCR 输出 → "默 / 认仓库"（中间有空格，排序错乱）
OpenOCR 输出   → "默认仓库"（score: 0.95，排序正确）
VLM 输出       → 文本框位于"入库"按钮下方

交叉校验结论 → "默认仓库" 是正确的，Windows OCR 的 "默 / 认" 是错别字
```

### 校验流程

```
┌─ 获取图片后 ───────────────────────────────────────────────┐
│                                                              │
│  1. Windows OCR 提取全量文本（覆盖率优先）                     │
│     powershell .qoder\skills\ocr\scripts\windows-ocr.ps1    │
│     -ImagePath "图片路径"                                     │
│     → 获取 blocks_count 和 blocks，确认是否有遗漏区域         │
│                                                              │
│  2. OpenOCR 提取精读文本（排序+置信度优先）                    │
│     python ocr_extract.py "图片路径" --json-blocks           │
│     → 获取带 score 的 blocks，以 score≥0.7 为可信基准         │
│                                                              │
│  3. Read 分析 UI 结构（布局理解）                             │
│     Read(file_path="图片路径")                               │
│     → 描述按钮/弹窗/表单/表格/颜色标记区域                    │
│                                                              │
│  4. 三通道交叉校验                                           │
│     - 同区域文本对比：Windows OCR × OpenOCR 暴露错别字         │
│     - 结构验证：Read 描述的 UI 元素在 OCR 结果中是否有对应文案  │
│     - 低置信度标记：OpenOCR score<0.7 的块，查 Windows OCR 同区域文本  │
│     - 遗漏检查：Read 发现 OCR 未提取区域 → 返回第 1 步补认    │
│                                                              │
└──────────────────────────────────────────────────────────────┘
```

### 典型场景决策

| 图片类型 | Windows OCR | OpenOCR | Read | 说明 |
|:---|:---:|:---:|:---:|:---|
| 纯文字截图/规则说明图 | — | ✅ 主 | — | OpenOCR 即可，无需其他通道 |
| 系统 UI 截图（按钮/弹窗/表格） | ✅ 辅 | ✅ 主 | ✅ | 三通道全开，Windows OCR 保覆盖率 |
| 多面板混合截图（复杂 UI） | ✅ 主 | ✅ 辅 | ✅ | Windows OCR 优先提取全量，OpenOCR 辅助排序 |
| 流程图/线框图 | ✅ 辅 | ✅ 主 | ✅ | OpenOCR 排序好，Windows OCR 防漏检小字 |
| 小字/装饰干扰（OCR 效果差） | ✅ 主 | — | ✅ 主 | 以 Windows OCR 覆盖 + Read 结构为主 |
| 原型图（颜色标记需求） | ✅ 辅 | ✅ 辅 | ✅ 主 | Read 识别颜色标记区域，OCR 提取对应文案 |

## 识图专项处理（通用能力）

以下专项处理属于本 skill 的通用识图能力，mcpcase / case-review 等调用方无需重复实现，直接由本 skill 处理：

### 浅灰小字处理

原型图注释面板中的浅灰小字，直接 OCR 可能识别失败：将对应区域裁剪后，用 Python（PIL）灰度化 + 对比度增强(2.5) + 亮度(1.2) + 放大 3-5 倍后再用 Read 读取。

### 双色标注通读（彩色标记分层）

原型图中**有颜色标记的注释与灰色/黑色说明文字需要分层处理**：有颜色标记的文字（红/蓝/橙/紫/绿等与背景可区分的彩色）是需求正相关内容（必须提取并作为用例依据，不限于红色）；灰色/黑色说明多为上下文参考（提取留作交叉验证），但其中若包含明确业务规则（字段约束/枚举选项/数值限制等）也须按兜底判断流程确认后作为用例依据。**删除线文字表示功能移除，不得作为用例依据**；**整张图无彩色标记（全黑）时推断为新功能，基于全部注释文本**。冲突时以 TAPD 描述为准并标记待确认项；识别结果需标注文本区域的颜色属性（彩色=需求正相关 / 黑色=参考 / 删除线=已移除）。

### 大图 bbox 相对坐标

>2000px 大图 OpenOCR 的 bbox 是列裁剪后的相对坐标，不能直接映射回原图裁剪；需按视觉位置裁剪。

## 工作流

### 主流程（推荐）

1. **Windows OCR 全量提取** → `powershell .qoder\skills\ocr\scripts\windows-ocr.ps1 -ImagePath "图片路径"`（获取覆盖率数据）
2. **OpenOCR 精读提取** → `python ocr_extract.py "图片路径" --json-blocks`（获取排序文本 + 置信度）
3. **Read 分析 UI 结构** → `Read(file_path="图片路径")`，记录按钮/弹窗/表单等元素
4. **三通道交叉校验** → Windows OCR vs OpenOCR vs Read 对比，发现遗漏和错别字
5. **低置信度处理** → 标记 OpenOCR score<0.7 的文本块，查 Windows OCR 同区域文本或 TAPD 原文确认
6. **校验** → 检查数字/特殊字符/文本顺序完整性
7. **交付** → 输出三通道融合后的纯文本 + UI 结构描述 + 置信度报告（如有低可信度块）

### 兜底：识别效果不佳时

当所有通道识别结果均明显不足（检测到文本块数量远少于肉眼可见量）时：

1. 确认当前自动化方案确实无法有效提取文字
2. **停止继续尝试自动化方案**（预处理增强、网格分割等方案已验证效果差）
3. **执行人工切图提示** → 告知用户：
   - 建议用截图工具将文字区域裁剪为独立小图
   - 或裁剪后拼接为长图再提供给 AI
   - 人工切图是当前最可靠的替代方案

### 用户提示

> ⚠️ **重要提示**：当前图片过于复杂（多面板重叠、小字号、UI 元素干扰），自动化方案无法可靠提取文字。请使用截图工具将图片中的文字区域逐一切割为独立小图（或拼接为长图），然后对小图逐一执行 OCR，或直接将拼接图提供给 AI 处理。**人工切图是当前最可靠的替代方案。**

## 置信度追踪

### 机制说明

OpenOCR 输出的每个文本块包含 `score` 字段（0~1），**三轨协同下置信度追踪升级为**：

1. **提取并记录每张图片的所有文本块及对应 `score`**（通过 `--json-blocks` 模式获取）
2. **标记 `score < 0.7` 的文本块**为「低可信度文本块」，这些区域的识别结果**不可靠**
3. 遇到低可信度文本块时，按以下优先级获取正确信息：
   - 🥇 **查 Windows OCR 同区域文本**：Windows OCR 对不同区域的识别精度可能不同，同区域文本可交叉验证
   - 🥇 **查 TAPD 需求描述原文**（`get_stories_or_tasks` 返回的 `description` 字段）
   - 🥇 **查 Spec 文档**（若有）
   - 🥉 **用 Read 工具复核图片**，但 Read 的描述必须与上述原文交叉校验
4. **禁止**将低可信度 OCR 文本直接作为用例预期结果/文案的依据

### 置信度报告

若存在 `score < 0.7` 的低可信度文本块，**必须**在本次对话末尾输出 OCR 置信度报告（Markdown 格式），**禁止写入任何文件**（包括测试用例文件和独立报告文件）。

**报告内容：**

```
## OCR 置信度报告

| 序号 | 图片文件 | OCR原文（低可信度） | 置信度 | 通道来源 | 可能影响的用例 | 说明 |
| :--- | :--- | :--- | :--- | :--- | :--- | :--- |
| 1 | xxx.png | 默认仓库 | 0.32 | OpenOCR | ①「入库默认仓库校验」 | 内容不可靠，需用户确认 |
| 2 | xxx.png | 缓荐 | - | Windows OCR | ②「缓存清空操作」 | 与 OpenOCR 同区域文本"缓存"冲突，需确认 |
```

**生成方法：**
1. 回顾执行过程中所有 OCR 调用的输出，提取 `score < 0.7` 的所有文本块（OpenOCR）以及 Windows OCR 中与 OpenOCR 高可信文本冲突的文本行
2. 对每个低可信度文本块，分析其内容可能影响的用例
3. 在报告末尾添加说明：
   > ⚠️ 以上 OCR 识别结果置信度低于 0.7，内容可能不准确。请用户逐条核对，确认无误或提供修正内容。

## 颜色标记识别规则（彩色标记+删除线识别）

### 核心原则

需求图片（尤其是注释面板）中通常包含三类文字：
- **彩色标记文字**（红/蓝/橙/紫/绿等任何与背景色可区分的彩色，含色框/色底高亮）：本次需求实际涉及的正相关内容，**必须作为用例编写的核心依据**；颜色用于识别正相关内容区域，而非限制用例范围
- **黑色/灰色背景文字**：多为上下文参考信息（操作流程/示例数据/通用说明），用于理解彩色标注的业务语境，一般**不**独立转化为测试用例；但其中若包含明确业务规则（字段约束/枚举选项/数值限制/状态流转），须按「颜色判定的兜底处理」确认后编写用例
- **删除线文字**：表示功能已移除，**不得**编写用例

> 典型场景：注释面板中彩色标注字段名、数值限制、状态流转逻辑（如"15字符"、"已分配→未分配"）；黑色文字说明背景操作流程（如"点击弹出激活码弹窗"）、示例数据、通用说明。
> **全黑图片兜底**：若整张图无任何彩色标记，推断为本次需求的新功能，基于全部注释文本编写用例，以 TAPD 需求描述交叉验证。

### 彩色文本 vs 黑色文本的用途分层

| 文本类型 | 颜色特征 | 用途层级 | 用例处理 |
| :--- | :--- | :--- | :--- |
| 需求变更点 | 🎨 任意彩色标记（红/蓝/橙/紫/绿等） | **核心** | 必须覆盖，是测试用例的主要预期依据 |
| 字段约束 | 🎨 彩色标注的数值限制/必填/格式 | **核心** | 必须编写边界值/异常流用例 |
| 状态流转 | 🎨 彩色标注的流转逻辑/条件分支 | **核心** | 必须编写对应状态组合的用例 |
| 操作结果 | 🎨 彩色标注的预期输出/提示文案 | **核心** | 直接作为预期结果 |
| 黑色文本中的业务规则 | ⬛ 明确约束/枚举/限制 | 核心（例外） | 按兜底判断流程确认后编写用例 |
| 操作流程 | ⬛ 黑色说明 | 参考背景 | 理解彩色标注的操作路径，不独立编写 |
| 示例数据 | ⬛ 灰色/黑色示例值 | 参考背景 | 仅用于理解字段格式，不代表测试数据 |
| 通用说明 | ⬛ 黑色背景解释 | 参考背景 | 不做用例依据 |
| 菜单/面板标题 | ⬛ 黑色标题 | 参考背景 | 不编写用例 |
| 已移除功能 | ~~删除线文字~~ | 排除 | 功能已移除，不得编写用例 |

### 三通道协同识别颜色标记

1. **Read 通道（主）**：先分析图片中哪些区域带有颜色标记（彩色文字/框/高亮），区分彩色正相关区域与黑色背景区域，输出布局结构时**标注每个区域的文本颜色属性**（含删除线区域）
   - 如有颜色标注，在描述中说明："彩色区域：XXX；黑色区域：XXX；删除线：XXX"
   - 如整张图无颜色标记（全黑白），**推断为新功能**，全部注释文本视为需求正相关，以 TAPD 需求描述交叉验证
2. **OCR 通道（辅）**：对**彩色标记区域**优先提取精确文案；黑色区域做全量提取留作上下文交叉验证与业务规则兜底判断
3. **交叉验证**：确认颜色标记区域与提取文案的对应关系；彩色区域 OCR 必须是高置信度（score≥0.9）才能作为用例依据

### 注释面板特殊处理

注释面板是颜色混排的高发场景，执行以下处理：
1. Read 识别每个注释条目中哪些部分带有彩色标记/删除线
2. 彩色标注内容 → 记录为"需求正相关"，必须出现在用例中
3. 黑色说明内容 → 记录为"上下文参考"，仅在理解彩色标注的语境时引用，一般**不**独立编写用例；若包含明确业务规则（字段约束/枚举选项/数值限制）且无法判断是否属于需求范围，标记"⚠️ 待确认"
4. 删除线标注内容 → 记录为"已移除功能"，**不得**编写用例
5. 如 Read 无法区分颜色（低保真原型图），则以 TAPD 需求描述中的重点标注为依据
6. **全黑图片**：推断为新功能，全部注释文本为用例依据

### 颜色判定的兜底处理

- 若 OCR 无法区分颜色（纯文字提取），且 Read 也无法明确判断颜色标记 → 按「5 步兜底判断流程」处理：TAPD 原文 → Spec 文档 → 知识库查询 → dbx 表结构 → 仍不确定则标记待确认
- 若同一图片中存在多种颜色标记，**所有彩色标记均为需求正相关**，一视同仁地编写用例，无需区分主次；无法确认是否属于需求范围的标记为待确认项
- 调用方（mcpcase / case-review）使用 OCR 结果时，**必读**本规则并按彩色标记分层处理：彩色区域文本写用例，黑色区域文本一般作上下文理解（含明确业务规则时兜底判断后编写），删除线文本排除

### 执行检查清单

颜色标记识别完成后，自检以下条目：
- [ ] 彩色标记区域是否全部提取（无遗漏正相关内容，不限于红色）
- [ ] 全黑图片是否按新功能处理（全部注释文本为用例依据）
- [ ] 删除线文本是否识别并排除（不编写用例）
- [ ] 黑色背景文本是否误作为用例依据；含明确业务规则的是否走了兜底判断流程
- [ ] 注释面板中彩色标注与黑色说明是否分别归类
- [ ] 跨通道验证：Read 识别为彩色的区域，OCR 是否都有对应文案
- [ ] 调用方使用的 OCR 结果中是否标注了文本所属区域的颜色属性

## 输出校验规则

对三通道融合后的结果进行检查：

- **数字完整性**：检查需求ID、单价、数量等数字串是否完整
- **遗漏检查**：与图片对照，检查是否有明显遗漏的文字区域
- **特殊字符**：检查 ②、【】、￥、/ 等是否准确
- **置信度一致性**：三通道同区域文本的置信度是否一致（低分冲突需标记）
- 发现问题，可对问题区域单独调用对应通道补识别

## 关键原则

| 原则 | 说明 |
|:---|:---|
| ✅ 三轨协同 | Windows OCR 保覆盖率，OpenOCR 保排序+置信度，Read 保结构理解 |
| ✅ 交叉验证 | 三通道同区域文本互相印证，错别字在对比中暴露 |
| ✅ 置信度驱动 | OpenOCR 的 score 字段作为可信度标尺，<0.7 需原文校验 |
| ✅ 像素级 OCR | 两个 OCR 引擎都是逐字符识别，不做语义概括/改写 |
| ✅ UI 结构识别 | Read 工具分析按钮/弹窗/输入框/下拉/表格等元素的位置和关系 |
| ✅ 防幻觉 | 像素级引擎不会编造文字内容，Read 基于实际可见元素描述 |
| ✅ 彩色标记分层 | 彩色标记文本（红/蓝/橙/紫/绿等）是需求正相关（用例依据），黑色文本是上下文参考（含明确业务规则时兜底判断），删除线文本表示功能移除 |
| ✅ 容忍轻微重复 | 相邻切块重叠可能导致少量文本重复，不影响整体可读性 |

## 已知限制

### Windows OCR 通道
- 仅支持 Windows 10+（依赖 Windows.Media.Ocr API）
- 对倾斜文字、手写体识别精度下降
- 文字顺序受布局影响，跨列排列时排序不自然
- 无置信度字段

### OpenOCR 通道
- OpenOCR 使用 OpenCV 加载图片，**不支持含中文的图片路径**（脚本已自动复制到临时目录规避）
- 首次运行需下载模型（~37MB），后续使用缓存
- 识别速度：每张图约 8~10 秒（mobile 模型）
- 对极小字号（<10px）、手写体、艺术字、倾斜文字识别精度下降
- **多区域图片**：自动裁剪对左右列分的布局效果最佳（左面板 + 右侧标注框）。如果图片由多个区域混合排列（如 2×2 网格），自动裁剪可能无法有效分离，此时可加 `--no-crop` 回退后，手动裁剪问题区域单独识别
- **文字顺序**：自适应排序算法大幅改进了旧版的行交叉问题，但跨列布局中细粒度顺序编排仍可能不完美
- **复杂 UI 截图处理极限**：对多面板重叠、小字号、带大量 UI 装饰元素的截图，检测模型可能无法有效分离文字与装饰元素。**此时以 Windows OCR 通道为主覆盖**

### 结构通道
- Read 输出为概括性描述，不能替代 OCR 的精确文字提取
- 对颜色标记的识别依赖图片本身的视觉区分度
- GLM 为可选第二意见：小字/数字/长段规则易丢失且存在幻觉风险（实测漏商品行、单价混淆），不得单独作为用例依据
- GLM 依赖 `GLM_API_KEY`（位于 Windows 用户环境变量 User scope，需 `[Environment]::GetEnvironmentVariable("GLM_API_KEY", "User")` 读取注入）
