# TAPD 需求测试用例核查（Review）

## 使用方式

用户输入**纯数字**（如 `1015691`）或带前缀（如 `/testcase-reviewer 1015691`）时，自动识别为需求 ID，按本 Skill 完整流程执行核查。

> 与 testcase-generator 的分工：testcase-generator 负责**生成**用例，本 Skill 负责**核查**既有用例与 TAPD 需求/原型图的一致性。本 Skill 不生成新用例。

## 完整执行流程总览

> ⚠️ 先看这里：下方章节按动作组织，实际执行顺序以本总览为准，严禁跳步。

| 顺序 | 执行动作 | 必须 | 条件触发 |
| :--- | :--- | :---: | :--- |
| 0 | 读取项目配置（`config/project.config.json`，不存在时提示 `/setup` 不中断流程）+ 通读团队记忆库（`.qoder/team-memory/`）README 索引及与本次任务相关的主题文件 | ✅ | |
| 1 | 定位双路径用例文件 | ✅ | |
| 2 | 获取 TAPD 需求信息（含父需求、评论、附件） | ✅ | |
| 3 | 复用/下载需求原型图（优先复用缓存，缺失才下载） | ✅ | 需求描述含 `<img>` |
| 4 | 调用 `/ocr` skill 三轨协同识图（多图并行，见第四步） | ✅ | 有原型图 |
| 5 | ⚡ 逐条比对核查（分层加速模式）| ✅ | |
| 6 | 有据项批量修正 + 输出核查报告 | ✅ | |
| 7 | 按用户确认结果修正待确认项（双路径同步） | ✅ | 有待确认项且用户确认后 |
| 8 | 清理临时文件 + 经验沉淀 | ✅ | |

> ⚡ **无图快速通道**：需求描述不包含 `<img>` → 跳过步骤 3~4，从步骤 5 直接开始文本级比对。

## 第一步：定位双路径用例文件

在以下两个目录查找 `{需求ID}-*.md`：

| 路径 | 说明 |
| :--- | :--- |
| `workspace/testcases/{迭代}/` | 正式路径 |
| `workspace/personal/drafts/{迭代}/` | 个人副本 |

- **hotfix 与迭代同目录**：hotfix 需求用例不再单独存 hotfix 目录，与迭代需求同目录定位（如 1019782 在 s92 目录下查找）
- **姓名子目录由用户自建**：正式目录下可能按姓名分目录（如 `{姓名缩写}\`），由用户自行维护；AI 定位/归档时直接使用 `testcases/{迭代}/` 平铺路径，不创建姓名目录
- **路径自愈**：目录缺失时自动创建，不因路径不存在中断流程

- 迭代名称（s90/s91/s92...）从 TAPD 返回的迭代信息确定，或从目录中已有文件推断
- 读取两份文件，确认内容一致；若仅存在一份，报告中注明
- **两份都不存在**：告知用户本 Skill 仅核查既有用例，建议先按 testcase-generator 生成用例再核查（除非用户明确要求直接核查）

## 第二步：获取 TAPD 需求信息

调用 `get_stories_or_tasks`（workspace_id 从 `config/project.config.json` 的 `tapd.workspace_id` 读取，下同；配置不存在时提示运行 `/setup` 或动态获取，不中断流程）：

```
workspace_id={workspace_id}, options={"entity_type":"stories","id":"{需求ID}","fields":"id,name,description,iteration_id,parent_id,status,creator"}
```

- **`entity_type` 必须传**（`"stories"`），否则返回空——最常见坑
- `fields` 必须包含 `description`（需求详细描述）
- 从 description 提取：需求概述、变更点、`<img>` 图片路径列表（形如 `/tfl/captures/...`）
- 有 `parent_id` 时，再查一次父需求（可能含补充说明）
- 查询评论（`get_comments`）与附件（`get_entity_attachments`），可能有补充信息
- **只分析 TAPD 描述中的内嵌图**，不扫描缓存目录里的历史图片（用户既定规则）；但缓存目录 `workspace/personal/image-cache/{需求ID}/` 中与 TAPD 描述 `<img>` **同名**的文件视为本需求缓存图，第三步**优先复用**（testcase-generator 生成用例后默认保留，核查无需重复下载）

## 第三步：复用/下载原型图（缓存一致性校验 + 优先复用）

> ⚡ **无图快速通道**：若第二步提取的 `<img>` 列表为空，直接跳过本步与第四步，进入第五步文本级比对。

缓存目录：`workspace/personal/image-cache/{需求ID}/`（不存在则创建）
缓存清单：同目录下 `.manifest.json`（`download_images.js` 下载时**自动**记录每图 md5/size/cached_at，无需手工维护）

**图片一致性校验（重要）**：产品可能在 TAPD 中更新需求图片，且新图 URL/文件名可能**不变**（同名覆盖）。为避免基于过期缓存图核查，复用前必须判断缓存与实时图是否一致：
1. **判定缓存是否可复用**：缓存目录存在同名文件 **且** manifest 有该图记录 **且** 缓存未超过 7 天 **且** 未指定 `--refresh` → 候选复用；任一不满足 → 直接下载（见下）
2. **候选复用图做实时校验**：对该图调用 `get_image` 获取实时 download_url，执行校验模式：
   ```
   node .qoder/skills/testcase-reviewer/scripts/download_images.js --verify {参数文件}
   ```
   参数文件格式：`[{"url":"{download_url}","out":"{缓存目录}/{原始文件名}"}, ...]`（校验模式自动从 manifest 读取记录的 size 与实时图 Content-Length 比对，仅发 Range 请求头不下载全量）
   - 输出 `VERIFY OK` → 实时图与缓存图一致，**复用缓存**
   - 输出 `VERIFY CHANGED` → 图片内容已更新，**重新下载**（见下，覆盖旧缓存）
   - 输出 `VERIFY UNKNOWN`（无 manifest 记录/网络异常）→ 保守处理，**重新下载**
3. `--refresh` 强制刷新：用户输入 `{需求ID} --refresh` 或明确要求忽略缓存时，跳过复用与校验，全部重新下载
4. 全部命中且校验一致 → 跳过下载环节，直接进入第四步识图

下载缺失/失效图片：
1. 对每张需下载图片调用 `get_image` 获取 download_url：
   ```
   workspace_id={workspace_id}, options={"image_path":"{图片路径}"}
   ```
   - **每次只能请求一张**；下载链接**默认有效 300s**，超时需重新调用
2. 将 `[{"url":"{download_url}","out":"{缓存目录}/{原始文件名}"}, ...]` 写入临时参数文件，执行：
   ```
   node .qoder/skills/testcase-reviewer/scripts/download_images.js {参数文件}
   ```
   （下载成功自动写入/更新 `.manifest.json`）
3. 失败（链接过期/网络错误/文件过小）时：重新调用 `get_image` 刷新链接后重试
4. 下载完成后删除参数文件
5. **下载统一用 TAPD 原始文件名命名**（与 basename 一致），保证下次核查可按同名复用；禁止自定义重命名（如 img1_xxx.png）

> ⚠️ 复用校验与下载共用同一批 `get_image` 返回的 download_url（300s 有效），务必在有效期内完成；校验模式不下载全量，配额成本远低于重复下载。
> ⚠️ 禁止用 PowerShell 脚本处理含中文的路径（PowerShell 5.1 按 ANSI 读无 BOM 的 UTF-8 脚本，中文路径会解析成乱码目录），统一用 Node 脚本。

## 第四步：三轨协同识图（调用 `/ocr` skill，多图并行）

> ⚡ **无图快速通道**：若第三步不需要下载/复用任何图片，直接跳过本步进入第五步。

**统一通过调用 `/ocr` skill 完成识图**（不直接调用脚本）。

### 多图并行优化

对多张待核查图片，**并行调用 `/ocr` skill**——在同一轮次中同时发起多个 Skill 调用（每张图片一个），并发等待所有结果返回，将多图 OCR 耗时从「逐张串行 × N 张」降为「≈ 单次最慢图」：

| 模式 | 耗时 | 适用 |
| :--- | :---: | :--- |
| 并行（推荐） | O(最慢单张) | 图片数目 ≥ 2 张，且图片间无依赖 |
| 串行（兜底） | O(Σ 每张耗时) | 并行后结果不完整/需要重试的单张 |

> **注意**：并行调用时确保每张图片独立参数（路径）、独立处理，结果合并后统一进行交叉验证；若某张图片 OCR 失败，单独重试该张即可，不影响其他图片。

由 /ocr 完成三轨协同识图、交叉验证、置信度追踪与兜底处理，直接使用其返回的三通道融合结果：

| 通道 | 职责 |
| :--- | :--- |
| Windows OCR（覆盖率） | 全量文本提取，不漏小字/装饰区域文字 |
| OpenOCR（精读排序） | 排序自然、置信度打分 |
| Read（结构理解） | UI 布局、按钮/弹窗/表格、颜色标记（按配置 color_legend 语义区分） |

**识图坑点**（由 /ocr 负责，核查阶段需关注结果层面的问题）：
- **OCR score < 0.7 的文本块**：以 TAPD 原文或其他通道反查校验，报告中注明
- **彩色标记分层比对（重要）**：原型图中**有颜色标记的注释是需求正相关内容**（重点比对对象，必须逐条核对用例覆盖）。**颜色语义从配置 `color_legend` 读取（各团队可自定义；默认图例：红色=本次迭代修改（核心变更点）、紫色=开发中临时改动（正相关）、橙色=未实现或他人并行修改（须以 TAPD 描述/开发评论交叉验证是否属于本次需求，属他人并行修改的不得要求覆盖）、黑色=原始逻辑/纯新增）**；蓝/绿等其他与背景可区分的彩色按正相关兜底处理；**灰色/黑色说明文字多为上下文参考**（用于交叉验证冲突，如默认值、文案差异，一般**不作为修正/补充用例的依据**；但黑色文本中含明确业务规则——字段约束/枚举选项/数值限制——时须核对用例是否覆盖）；**删除线文字表示功能移除**（用例若覆盖已移除功能需标记修正/删除）；**全黑图片推断为新功能**，全部注释文本均须核对用例覆盖
- 浅灰小字、大图 bbox 相对坐标、GLM 第二意见、人工切图兜底等处理细节见 `.qoder/skills/ocr/SKILL.md`，本 skill 不再重复实现

## 第五步：逐条比对核查（分层加速模式）

**核心提速原则：按优先级分层比对，彩色标记正相关内容全覆盖 → 剩余用例快速过筛 → 最后逐条精校**。在保证质量（彩色标记正相关内容无遗漏）的前提下，避免对每条用例都做同等粒度的精细比对。

### 第一层：变更点反向映射（必检，确保覆盖无遗漏）

提取 OCR 识图结果中**彩色标记的正相关内容**（字段约束/状态流转/操作结果/选项值，含红/紫及蓝/绿等其他可区分彩色，橙色须先验证范围；全黑图片按新功能处理，基于全部注释文本），逐一确认：
- 每个变更点**至少 1 条用例覆盖**（通过「关联引用」列或语义匹配定位）
- 覆盖该变更点的用例**预期结果是否与原型原文一致**
- 有遗漏 → 标记为 ➕ 有据补充

**检出未覆盖的变更点**后，标记全部收集汇总后**统一补充**（不逐一调用 SearchReplace，见第六步批量修正模式）。

### 第二层：优先级快速过筛（抽样验证，降低比对量）

对变更点映射剩余的用例，按以下优先级快速过筛——优先级低的用例**抽样比对**而非逐条全量比对：

| 用例类型 | 优先级 | 比对策略 |
| :--- | :---: | :--- |
| 变更点反向映射的用例 | P0 | 逐条全量比对 |
| 正向功能流程（未映射至变更点的） | P1 | 逐条快速比对（仅确认预期结果是否合理） |
| 边界值测试 / 异常输入 | P2 | 抽样 30%（确认边界值是否基于原型实际限制；无明确限制的不细究） |
| 按钮防抖 | P3 | 跳过（testcase-generator 强制规范，不得删除/质疑） |
| 纯 UI 描述用例（位置/布局/颜色） | P3 | 跳过（原型图 UI 细节不作为预期依据，见 Skill 禁止规则） |
| 空态/默认文案（原型未标注） | P3 | 跳过（原型未说明则不推断） |

> **质量保障**：P0 变更点映射的用例必须逐条全量比对；P1 快速比对确保不出现明显逻辑错误；P2 抽样确认边界值合理；P3 跳过项均为 skill 规范已确定的规则，跳过不降低质量。

### 第三层：逐条精校（存量用例最终校验）

对 P0+P1 层用例，按以下维度逐条精校：

| 分类 | 定义 | 处理 |
| :--- | :--- | :--- |
| ✅ 一致 | 用例与原型/需求一致 | 无需处理 |
| 🔧 有据直接修正 | 原型注释/TAPD 描述原文明确与用例冲突，或明显笔误（字段名、默认值、选项值、数值限制） | 直接双路径修正，报告列出原型依据原文 |
| ➕ 有据补充 | 原型有但用例未覆盖（筛选项、字段、交互、状态） | 直接补充用例并同步矩阵，报告给出草案与依据 |
| 🗑️ 有据删除 | 用例有但原型字段清单/TAPD 描述均无（纯推断项） | 直接删除并同步矩阵，报告注明"如业务实际存在可告知恢复" |
| ⚠️ 待确认 | 原型内部多表述冲突无法定夺 / OCR score<0.7 无法反查 / 业务口径原型未明 | 列出原型原文依据，等用户确认 |

**有据 vs 待确认判定标准**（核心原则：结论是否唯一）：
- **可直接修正**：证据链完整、结论唯一——原型注释原文（OCR 双通道验证且 score≥0.7）、TAPD 描述原文、开发评论接口说明（字段名/状态值/统计口径）
- **必须待确认**：① 原型内部两处及以上表述冲突且无法判定等价性；② OCR score<0.7 且无法以其他通道反查；③ 用例推断项原型与描述均未涉及但属业务决策（如数据源范围、权限来源）；④ 防抖用例（testcase-generator 规范"防抖必测"，不得建议删除）；⑤ 空态/默认文案原型未标注

### 比对维度
- 文案差异：提示语、按钮文字、弹窗标题（如"请先选择门店" vs "请选择适用门店"）
- 选项值：全部/是/否 vs 全部/有/无
- 默认值：默认选择 vs 默认不选择
- 交互逻辑：单选/多选、开关状态、切换时清除数据范围
- 数值限制：字数、位数（如扫一扫截取前 40 位）、范围、条数
- 数据源与权限控制
- **颜色属性校验**：比对依据中彩色标注文本优先（需求正相关，红/紫及蓝/绿等其他可区分彩色；橙色先验证范围），黑色文本仅参考（含明确业务规则时核对是否覆盖）；若用例大量源自黑色说明文字，需审查是否越界；用例覆盖删除线文本对应功能时，需确认是否应修正/删除
- 按钮防抖：依据 testcase-generator 规范"按钮防抖必测"，**不得建议删除防抖用例**
- 空态：原型未说明则不推断、不补充

## 第六步：批量修正模式（先收集、后统一执行）

**核心提速：先收集所有有据修正项，一次性批量执行 SearchReplace，仅最终做一次哈希验证。** 避免逐条修正的反复 SearchReplace + md5 I/O 开销。

### 执行流程

1. **收集阶段**：将 Step 5 检出的所有 🔧/➕/🗑️ 修正 → 统一记入「修正清单」：
   - 🔧 修正项：`{原文本 → 新文本}` 逐条列出（标明文件位置/行号）
   - ➕ 补充项：`{用例名称 + 前置条件 + 操作步骤 + 预期结果}` 完整草案
   - 🗑️ 删除项：`{用例名称}` 逐条列出
2. **整合阶段**：将同类修正合并为一个 SearchReplace 调用的 `replacements` 数组（每处一个元素）
3. **执行阶段**：对每份文件**各调用一次 SearchReplace**（含所有 replacement），单次提交
4. **验证阶段**：两份文件修改完成后，统一做一次 Node md5 哈希比对，确认同步一致
5. **矩阵同步**：增删后同步更新测试覆盖矩阵的数量与合计
6. **输出核查报告**

> **注意**：若修正项跨多个段落，按在文件中的出现顺序排列 replacements；合并前 `original_text` 必须确保唯一性，避免误替换。

再输出报告。**有据修正与待确认修正都须双路径同步**（正式路径 + 个人副本），并同步更新测试覆盖矩阵数量与合计、文件末尾记录修正说明。

按以下模板输出：

```
## 核查报告：{需求ID} {需求标题}

**需求信息**：迭代 | 原型图 N 张 | 用例文件位置（双路径是否一致）
**比对结果**：一致 N 条 | 有据直接修正 N 条 | 补充用例 N 条 | 删除用例 N 条 | 待确认 N 条

### 已直接修正（依据明确，已同步双路径）
1. 修正内容（原写法 → 新写法）｜原型依据原文

### 已补充用例（原型有、用例无，已同步双路径）
1. 用例名称与要点 ｜ 原型依据原文

### 已删除用例（原型与描述均无，已同步双路径）
1. 用例名称 ｜ 删除依据（如业务实际存在可告知恢复）

### 待确认项（等用户确认）
1. ...（列出原型原文依据，便于用户复核）
```

## 第七步：待确认项确认后双路径同步修正

用户对待确认项给出结论后，**同步修改两份文件**（正式路径 + 个人副本），保持内容一致：

1. 仅按确认结果修正待确认项（口径取舍、歧义定夺）
2. 增删用例后**必须**同步更新测试覆盖矩阵的数量与合计
3. 文件末尾记录更新为"已确认 {YYYY-MM-DD}"，逐条注明确认结果与依据
4. 关联需求联动检查：涉及两端（如门店端/总部端）相同功能时，检查是否需要联动修正并提示用户
5. 用户确认文案与原型文字不一致时，以用户确认文案为准，但记录中注明差异依据

**双路径同步与记录规范**（第六步直接修正同样适用）：
- **批量执行**：收集全部修正项后，对每份文件**各调一次 SearchReplace**（含所有 replacement），不逐条操作
- **最终验证**：两份文件修改完成后，统一做一次 Node md5 哈希比对确认一致（**不再每条修正都验证**），减少 I/O 开销
- 增删用例后同步矩阵数量与合计，避免文档自相矛盾
- 文件末尾说明：直接修正记录为"已修正 {YYYY-MM-DD}（有据直接修正）：逐条注明原型依据原文"；待确认项保留在报告中，用户确认后追加"已确认 {YYYY-MM-DD}"记录

## 第八步：清理与沉淀

1. 删除本次任务的全部临时文件：下载参数文件、OCR 输出、裁剪图、包装脚本
2. **扫描项目根目录的一次性脚本/产物**：`_*.py`、`_*.js`、`_*.png`、`_*.txt` 等下划线开头的临时文件，确认无用后全部删除
3. 删除后**必须验证**：再次列出目录确认已清空；若 DeleteFile 工具返回成功但文件仍存在（工具对部分文件失效），改用 PowerShell `Remove-Item -Force` 兜底删除
4. **乱码目录检查**：任务结束检查 `workspace/` 下是否存在乱码名目录（PowerShell ANSI 乱码残留，如"鎴戠殑鏂囦欢"）；删除乱码目录树必须用 Python 脚本先验证名称码位与正确目录不同，防止误删正确目录
5. 保留：缓存目录中的原型图（供后续核查复用；**下次核查按 TAPD img 同名匹配优先复用**，见第三步）
6. 有价值的坑点/结论更新到 `.qoder/team-memory/` 或本 Skill 参考文件

## 关键坑点速查

| 坑点 | 影响 | 规避 |
| :--- | :--- | :--- |
| `get_stories_or_tasks` 不传 entity_type | 返回空 | options 必传 `entity_type: "stories"` |
| `get_image` 链接 300s 过期 | 下载到 13 字节文件或失败 | 超时重新 get_image 刷新链接 |
| PowerShell 5.1 读无 BOM UTF-8 脚本 | 中文路径乱码目录 | 用 Node/Python 脚本处理路径 |
| 大图 OCR bbox 为列裁剪相对坐标 | 按 bbox 裁剪位置错误 | /ocr 已内置处理，按视觉位置裁剪 |
| 浅灰小字裁剪后识别失败 | 误判文案 | /ocr 已内置处理（灰度 + 增强 + 放大后 Read） |
| OCR score < 0.7 | 可能识别错误 | TAPD 原文/Read 反查校验 |
| 扫描缓存目录历史图 | 混入非本需求图片 | 只分析 TAPD 描述内嵌图；仅复用 `{需求ID}/` 目录下与 `<img>` 同名的缓存图 |
| 缓存已有本需求同名图仍重复下载 | 浪费 get_image 配额与时间 | 第三步按 basename 优先复用，缺失才下载 |
| 缓存图自定义重命名（img1_xxx.png） | 下次无法按 basename 匹配复用 | 下载统一用 TAPD 原始文件名 |
| TAPD 同名图片内容被更新（同名覆盖） | 静默复用过期缓存图，核查基于旧图 | 复用前 `--verify` 比对实时 Content-Length 与 manifest 记录，CHANGED/UNKNOWN 一律重下 |
| 旧缓存无 manifest 记录 | 无法校验，复用不可靠 | verify 输出 UNKNOWN 时保守重下，下载后自动补写 manifest |
| 双路径不同步 | 两份文件版本不一致 | 每次修改同步两份 |
| 矩阵数量不同步 | 文档自相矛盾 | 增删用例后同步计数与合计 |
| DeleteFile 返回成功但文件未删除 | 临时文件残留、清理不彻底 | 删除后重新列出验证，必要时用 PowerShell `Remove-Item -Force` 兜底 |
| 命令行传乱码名会被 PowerShell 按 ANSI 解码成正确名 | 误删正确目录 | 删除乱码目录树用 Python 脚本验证名称码位后执行 |
