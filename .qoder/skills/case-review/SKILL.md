# TAPD 需求测试用例核查（Review）

## 使用方式

用户输入**纯数字**（如 `1015691`）或带前缀（如 `/case-review 1015691`）时，自动识别为需求 ID，按本 Skill 完整流程执行核查。

> 与 mcpcase 的分工：mcpcase 负责**生成**用例，本 Skill 负责**核查**既有用例与 TAPD 需求/原型图的一致性。本 Skill 不生成新用例。

## 完整执行流程总览

> ⚠️ 先看这里：下方章节按动作组织，实际执行顺序以本总览为准，严禁跳步。

| 顺序 | 执行动作 | 必须 | 条件触发 |
| :--- | :--- | :---: | :--- |
| 0 | 通读团队记忆库（`.qoder/team-memory/`）README 索引及与本次任务相关的主题文件 | ✅ | |
| 1 | 定位双路径用例文件 | ✅ | |
| 2 | 获取 TAPD 需求信息（含父需求、评论、附件） | ✅ | |
| 3 | 复用/下载需求原型图（优先复用缓存，缺失才下载） | ✅ | 需求描述含 `<img>` |
| 4 | 调用 `/ocr` skill 三轨协同识图（Windows OCR + OpenOCR + Read） | ✅ | 有原型图 |
| 5 | 逐条比对核查（分类：一致 / 有据直接修正 / 待确认） | ✅ | |
| 6 | 有据项直接双路径修正 + 输出核查报告（已改项 + 待确认项） | ✅ | |
| 7 | 按用户确认结果修正待确认项（双路径同步） | ✅ | 有待确认项且用户确认后 |
| 8 | 清理临时文件 + 经验沉淀 | ✅ | |

## 第一步：定位双路径用例文件

在以下两个目录查找 `{需求ID}-*.md`：

| 路径 | 说明 |
| :--- | :--- |
| `workspace/testcases/{迭代}/` | 正式路径 |
| `workspace/personal/drafts/{迭代}/` | 个人副本 |

- **hotfix 与迭代同目录**：hotfix 需求用例不再单独存 hotfix 目录，与迭代需求同目录定位（如 1019782 在 s92 目录下查找）
- **姓名子目录由用户自建**：正式目录下可能按姓名分目录（如 `{姓名缩写}\`），由用户自行维护；AI 定位/归档时直接使用 `testcases/{迭代}/` 平铺路径，不创建姓名目录
- **路径自愈**：目录缺失时自动创建，不因路径不存在中断流程

- 迭代名称（s90/s91/s92...）从 TAPD 返回的迭代信息确定，或从目录中已有文件推断
- 读取两份文件，确认内容一致；若仅存在一份，报告中注明
- **两份都不存在**：告知用户本 Skill 仅核查既有用例，建议先按 mcpcase 生成用例再核查（除非用户明确要求直接核查）

## 第二步：获取 TAPD 需求信息

调用 `get_stories_or_tasks`（workspace_id 从 `config/project.config.json` 的 `tapd.workspace_id` 读取，下同；配置不存在时提示运行 `/setup` 或动态获取，不中断流程）：

```
workspace_id={workspace_id}, options={"entity_type":"stories","id":"{需求ID}","fields":"id,name,description,iteration_id,parent_id,status,creator"}
```

- **`entity_type` 必须传**（`"stories"`），否则返回空——最常见坑
- `fields` 必须包含 `description`（需求详细描述）
- 从 description 提取：需求概述、变更点、`<img>` 图片路径列表（形如 `/tfl/captures/...`）
- 有 `parent_id` 时，再查一次父需求（可能含补充说明）
- 查询评论（`get_comments`）与附件（`get_entity_attachments`），可能有补充信息
- **只分析 TAPD 描述中的内嵌图**，不扫描缓存目录里的历史图片（用户既定规则）；但缓存目录 `workspace/personal/image-cache/{需求ID}/` 中与 TAPD 描述 `<img>` **同名**的文件视为本需求缓存图，第三步**优先复用**（mcpcase 生成用例后默认保留，核查无需重复下载）

## 第三步：复用/下载原型图（优先复用缓存）

缓存目录：`workspace/personal/image-cache/{需求ID}/`（不存在则创建）

**优先复用缓存**（与 mcpcase 缓存保留策略衔接，避免重复下载）：
1. 取第二步提取的每个 `<img>` 路径的**文件名 basename**（如 `tapd_{workspace_id}_base64_1785815252_413.png`）
2. 检查缓存目录中是否存在**同名文件**：
   - **存在** → 直接复用该缓存图，跳过下载
   - **不存在** → 该图需下载（见下）
3. 全部命中（复用 100%）→ 跳过下载环节，直接进入第四步识图

下载缺失图片：
1. 对每张缺失图片调用 `get_image` 获取 download_url：
   ```
   workspace_id={workspace_id}, options={"image_path":"{图片路径}"}
   ```
   - **每次只能请求一张**；下载链接**默认有效 300s**，超时需重新调用
2. 将 `[{"url":"{download_url}","out":"{缓存目录}/{原始文件名}"}, ...]` 写入临时参数文件，执行：
   ```
   node .qoder/skills/case-review/scripts/download_images.js {参数文件}
   ```
3. 失败（链接过期/网络错误/文件过小）时：重新调用 `get_image` 刷新链接后重试
4. 下载完成后删除参数文件
5. **下载统一用 TAPD 原始文件名命名**（与 basename 一致），保证下次核查可按同名复用；禁止自定义重命名（如 img1_xxx.png）

> ⚠️ 禁止用 PowerShell 脚本处理含中文的路径（PowerShell 5.1 按 ANSI 读无 BOM 的 UTF-8 脚本，中文路径会解析成乱码目录），统一用 Node 脚本。

## 第四步：三轨协同识图（调用 `/ocr` skill）

**统一通过调用 `/ocr` skill 完成识图**（不直接调用脚本）：对每张待核查图片，**调用 `/ocr` skill**（参数：图片路径），由 /ocr 完成三轨协同识图、交叉验证、置信度追踪与兜底处理，直接使用其返回的三通道融合结果：

| 通道 | 职责 |
| :--- | :--- |
| Windows OCR（覆盖率） | 全量文本提取，不漏小字/装饰区域文字 |
| OpenOCR（精读排序） | 排序自然、置信度打分 |
| Read（结构理解） | UI 布局、按钮/弹窗/表格、黄色标注等颜色标记 |

**识图坑点**（由 /ocr 负责，核查阶段需关注结果层面的问题）：
- **OCR score < 0.7 的文本块**：以 TAPD 原文或其他通道反查校验，报告中注明
- 原型图中的黄色/彩色标注注释与灰色说明文字**都要读**（两处常有冲突信息，如默认值、文案差异）
- 浅灰小字、大图 bbox 相对坐标、GLM 第二意见、人工切图兜底等处理细节见 `.qoder/skills/ocr/SKILL.md`，本 skill 不再重复实现

## 第五步：逐条比对核查

读取用例文件全部用例，与"TAPD 需求描述 + 原型注释原文"逐条比对，分类：

| 分类 | 定义 | 处理 |
| :--- | :--- | :--- |
| ✅ 一致 | 用例与原型/需求一致 | 无需处理 |
| 🔧 有据直接修正 | 原型注释/TAPD 描述原文明确与用例冲突，或明显笔误（字段名、默认值、选项值、数值限制） | 直接双路径修正，报告列出原型依据原文 |
| ➕ 有据补充 | 原型有但用例未覆盖（筛选项、字段、交互、状态） | 直接补充用例并同步矩阵，报告给出草案与依据 |
| 🗑️ 有据删除 | 用例有但原型字段清单/TAPD 描述均无（纯推断项） | 直接删除并同步矩阵，报告注明"如业务实际存在可告知恢复" |
| ⚠️ 待确认 | 原型内部多表述冲突无法定夺 / OCR score<0.7 无法反查 / 业务口径原型未明 | 列出原型原文依据，等用户确认 |

**有据 vs 待确认判定标准**（核心原则：结论是否唯一）：
- **可直接修正**：证据链完整、结论唯一——原型注释原文（OCR 双通道验证且 score≥0.7）、TAPD 描述原文、开发评论接口说明（字段名/状态值/统计口径）
- **必须待确认**：① 原型内部两处及以上表述冲突且无法判定等价性；② OCR score<0.7 且无法以其他通道反查；③ 用例推断项原型与描述均未涉及但属业务决策（如数据源范围、权限来源）；④ 防抖用例（mcpcase 规范"防抖必测"，不得建议删除）；⑤ 空态/默认文案原型未标注

**重点比对维度**（原型图注释优先于用例推断）：
- 文案差异：提示语、按钮文字、弹窗标题（如"请先选择门店" vs "请选择适用门店"）
- 选项值：全部/是/否 vs 全部/有/无
- 默认值：默认选择 vs 默认不选择
- 交互逻辑：单选/多选、开关状态、切换时清除数据范围
- 数值限制：字数、位数（如扫一扫截取前 40 位）、范围、条数
- 数据源与权限控制
- 按钮防抖：依据 mcpcase 规范"按钮防抖必测"，**不得建议删除防抖用例**
- 空态：原型未说明则不推断、不补充

## 第六步：有据项直接修正 + 输出核查报告

先执行有据修正（🔧/➕/🗑️ 类），再输出报告。**有据修正与待确认修正都须双路径同步**（正式路径 + 个人副本），并同步更新测试覆盖矩阵数量与合计、文件末尾记录修正说明。

按以下模板输出：

```
## 核查报告：{需求ID} {需求标题}

**需求信息**：迭代 | 原型图 N 张 | 用例文件位置（双路径是否一致）
**比对结果**：一致 N 条 | 有据直接修正 N 条 | 补充用例 N 条 | 删除用例 N 条 | 待确认 N 条

### 已直接修正（依据明确，已同步双路径）
1. 修正内容（原写法 → 新写法）｜原型依据原文

### 已补充用例（原型有、用例无，已同步双路径）
1. 用例名称与要点 ｜ 原型依据原文

### 已删除用例（原型与描述均无，已同步双路径）
1. 用例名称 ｜ 删除依据（如业务实际存在可告知恢复）

### 待确认项（等用户确认）
1. ...（列出原型原文依据，便于用户复核）
```

## 第七步：待确认项确认后双路径同步修正

用户对待确认项给出结论后，**同步修改两份文件**（正式路径 + 个人副本），保持内容一致：

1. 仅按确认结果修正待确认项（口径取舍、歧义定夺）
2. 增删用例后**必须**同步更新测试覆盖矩阵的数量与合计
3. 文件末尾记录更新为"已确认 {YYYY-MM-DD}"，逐条注明确认结果与依据
4. 关联需求联动检查：涉及两端（如门店端/总部端）相同功能时，检查是否需要联动修正并提示用户
5. 用户确认文案与原型文字不一致时，以用户确认文案为准，但记录中注明差异依据

**双路径同步与记录规范**（第六步直接修正同样适用）：
- 每次修正必须同步两份文件（正式路径 + 个人副本），修改后验证哈希一致（Node md5）
- 增删用例后同步矩阵数量与合计，避免文档自相矛盾
- 文件末尾说明：直接修正记录为"已修正 {YYYY-MM-DD}（有据直接修正）：逐条注明原型依据原文"；待确认项保留在报告中，用户确认后追加"已确认 {YYYY-MM-DD}"记录

## 第八步：清理与沉淀

1. 删除本次任务的全部临时文件：下载参数文件、OCR 输出、裁剪图、包装脚本
2. **扫描项目根目录的一次性脚本/产物**：`_*.py`、`_*.js`、`_*.png`、`_*.txt` 等下划线开头的临时文件，确认无用后全部删除
3. 删除后**必须验证**：再次列出目录确认已清空；若 DeleteFile 工具返回成功但文件仍存在（工具对部分文件失效），改用 PowerShell `Remove-Item -Force` 兜底删除
4. **乱码目录检查**：任务结束检查 `workspace/` 下是否存在乱码名目录（PowerShell ANSI 乱码残留，如"鎴戠殑鏂囦欢"）；删除乱码目录树必须用 Python 脚本先验证名称码位与正确目录不同，防止误删正确目录
5. 保留：缓存目录中的原型图（供后续核查复用；**下次核查按 TAPD img 同名匹配优先复用**，见第三步）
6. 有价值的坑点/结论更新到 `.qoder/team-memory/` 或本 Skill 参考文件

## 关键坑点速查

| 坑点 | 影响 | 规避 |
| :--- | :--- | :--- |
| `get_stories_or_tasks` 不传 entity_type | 返回空 | options 必传 `entity_type: "stories"` |
| `get_image` 链接 300s 过期 | 下载到 13 字节文件或失败 | 超时重新 get_image 刷新链接 |
| PowerShell 5.1 读无 BOM UTF-8 脚本 | 中文路径乱码目录 | 用 Node/Python 脚本处理路径 |
| 大图 OCR bbox 为列裁剪相对坐标 | 按 bbox 裁剪位置错误 | /ocr 已内置处理，按视觉位置裁剪 |
| 浅灰小字裁剪后识别失败 | 误判文案 | /ocr 已内置处理（灰度 + 增强 + 放大后 Read） |
| OCR score < 0.7 | 可能识别错误 | TAPD 原文/Read 反查校验 |
| 扫描缓存目录历史图 | 混入非本需求图片 | 只分析 TAPD 描述内嵌图；仅复用 `{需求ID}/` 目录下与 `<img>` 同名的缓存图 |
| 缓存已有本需求同名图仍重复下载 | 浪费 get_image 配额与时间 | 第三步按 basename 优先复用，缺失才下载 |
| 缓存图自定义重命名（img1_xxx.png） | 下次无法按 basename 匹配复用 | 下载统一用 TAPD 原始文件名 |
| 双路径不同步 | 两份文件版本不一致 | 每次修改同步两份 |
| 矩阵数量不同步 | 文档自相矛盾 | 增删用例后同步计数与合计 |
| DeleteFile 返回成功但文件未删除 | 临时文件残留、清理不彻底 | 删除后重新列出验证，必要时用 PowerShell `Remove-Item -Force` 兜底 |
| 命令行传乱码名会被 PowerShell 按 ANSI 解码成正确名 | 误删正确目录 | 删除乱码目录树用 Python 脚本验证名称码位后执行 |
