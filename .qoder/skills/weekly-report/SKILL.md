# 周报生成 Skill

## 使用方式

调用格式：

> `/zb Sprint90、hotfix-s90迭代 张三，7月20日-7月25日`

执行本 Skill 时需确认以下信息（若用户未提供则主动询问）：
1. **迭代版本**：Sprint 编号（如 S90）及 hotfix 迭代名称
2. **处理人**：周报归属人
3. **时间范围**：周报覆盖的起止日期

> 用户直接输入需求时，按 `<迭代> <处理人> <时间范围>` 格式解析。

## 数据来源规范

### TAPD MCP 调用规则

#### 1. 获取迭代信息
- 调用 `get_iterations`，通过 `workspace_id` + `name` 模糊匹配定位迭代
- 记录迭代 ID，用于后续需求/缺陷查询
- workspace_id 从 `config/project.config.json` 的 `tapd.workspace_id` 读取；配置不存在时通过 `get_user_participant_projects()` 动态获取（多项目时向用户确认），不得中断流程

#### 2. 获取需求列表
- 调用 `get_stories_or_tasks`，参数：
  - `entity_type`: "stories"
  - `iteration_id`: 迭代ID
  - `owner`: 处理人
  - `fields`: 至少包含 `id,name,status,owner,modified`
  - `limit`: 根据返回数量设置（建议 100）
- 按 `modified` 时间在目标范围内过滤（反映本周测试动作）

#### 3. 获取缺陷列表
- 调用 `get_bug`，参数：
  - `iteration_id`: 迭代ID
  - `reporter`: 创建人—— ⚠️ 使用 `reporter` 而非 `owner`
  - `fields`: 至少包含 `id,title,status,reporter,created,severity`
  - `limit`: 根据返回数量设置（建议 100）
- 按 `created` 时间在目标范围内过滤（反映本周新发现的缺陷）

> **注意**：TAPD 缺陷 API 的处理人字段为 `current_owner`，但缺陷流转后处理人可能被修改（如转给开发），导致漏计。推荐使用 `reporter`（创建人），因为创建人不可变，能准确反映测试人员本周亲自发现并提交的缺陷数。`owner` 参数在缺陷 API 中会被静默忽略，不可使用。

## 进度标注规则

### 通用版（适用于大多数成员）

| TAPD 状态码 | TAPD 中文名 | 周报进度标注 |
| :--- | :--- | :--- |
| resolved | 已实现 | （已实现） |
| status_5 | 验收中 | （验收中） |
| status_2 | 测试中 | （测试中） |
| developing | 实现中 | （实现中） |
| status_3 | 未开始 | （未开始） |
| status_4 | 待设计 | （待设计） |
| planning | 规划中 | （规划中） |
| rejected | 已拒绝 | （已拒绝） |

> 以上映射关系以 TAPD 工作流实时状态为准，可通过 `get_workflows_status_map` 接口获取最新映射。

### 需求分类规则

- **已提测需求**：状态为 resolved（已实现）/ status_5（验收中）/ status_2（测试中）的需求，列入「本周工作」对应迭代区域
- **未提测需求**：状态为 developing（实现中）/ status_3（未开始）/ status_4（待设计）/ planning（规划中）/ rejected（已拒绝）等未进入测试阶段的需求，列入「***未提测需求：***」区域，需附带 TAPD 链接

## 周报文件规范

- 文件名：`{年月日时间戳}-{姓名}-周报`
- 时间戳取周报结束日期，如 `20260718`
- 文件输出路径：`workspace/personal/weekly/{文件名}.md`（目录不存在则自动创建；路径模板见配置 `archive.weekly_dir`）

### 个人版填写规则

| 规则项 | 说明 |
| :--- | :--- |
| 迭代名写法 | `S{版本号}需求测试`（省略 sprint 前缀） |
| hotfix 标题 | 直接写 `hotfix：` |
| Sprint 进度标注 | 统一使用 `（进度100%）` |
| hotfix 发布状态 | 人为补充，生成时不标注 |
| 内容范围 | 仅列亲自经手且已完成的工作项 |
| hotfix 混排 | 需求和缺陷不严格区分，按实际工作内容列出 |
| 未提测 | ❌ 不写 |
| 优缺点总结 | ❌ 不写段落文字，仅列出 `【【优化】...（详情）】` 一行 |
| 优化缺陷 | 不附加 TAPD 链接，格式为 `【【优化】{标题}（详情）】` |
| 新增章节 | `2、UAT&P0验收` 和 `3、S{next}测试用例编写（进度X%）` |
| 下周计划 | 概要性一句话描述，不详细拆解 |

## 执行流程

### 第一步：确认输入信息
- 向用户确认：迭代版本、处理人、时间范围
- 若用户直接提供了，跳过确认

### 第二步：获取迭代信息
- 调用 `get_iterations(workspace_id={workspace_id})` 获取所有迭代（workspace_id 取自配置，见数据来源规范第 1 节）
- 根据迭代名称匹配目标迭代（主干迭代 + hotfix 迭代）
- 记录迭代 ID

### 第三步：获取需求数据
- 对每个目标迭代，调用 `get_stories_or_tasks` 获取需求列表
- 按处理人 + modified 时间范围过滤

### 第四步：获取缺陷数据
- 对每个目标迭代，调用 `get_bug` 获取缺陷列表
- 按创建人（reporter）+ created 时间范围过滤

### 第五步：生成周报
- 若用户偏好简洁风格，则按**精简版模板**生成；否则按**通用模板**生成
- 按文件规范保存到 `workspace/personal/weekly/` 目录
- 在对话回复中补充**数据说明**：

  > **数据说明**：以上需求列表按 TAPD 迭代 + 处理人 + modified 时间范围筛选，缺陷列表按迭代 + 创建人（reporter）+ created 时间范围筛选。生成内容不代表本人在所提供时间段内操作了所有状态变更，如需求的其他处理人（如产品、开发）变更状态也会被计入 modified 时间范围。
